## 结论摘要

- Agent 能力强不等于时间控制稳定。AgentTime 的 222 个任务覆盖 18 个基准和 1.25 分钟至 72 小时目标时长，最强系统在 ±5% 目标窗口内完成的比例也只有 63%。
- 旧系统明显提前结束：Claude Fable 5.1 的实际时长随目标时长的对数斜率只有 0.59；GPT-5.6 Sol 为 0.71；GPT-6 Astra 提高到 0.94，但仍存在系统性偏差。
- 延长运行时间没有稳定提升任务得分。最长与最短时限的平均得分都在 62%～64%，只有 23%～25% 的任务在更长时限下表现更好。
- 开放代码的 196 项测试通过，但当前仓库仍把早期 235 题预测实验与论文中的 222 题时间控制实验分开；主实验完整复现入口尚未全部公开。

## 研究问题与背景

真实 Agent 服务需要按时完成：用户可能要求「工作 10 分钟后给结果」，编排器也需要预测资源和截止时间。已有评测通常只看任务是否完成或 token 上限，很少测量 Agent 是否理解目标时长、能否主动分配时间，以及延长运行时间是否真的改善结果。

论文把时间能力拆为三层：执行前预测任务需要多久；收到明确时限后控制实际运行时间；执行后从轨迹回顾真实时长。Agent 的状态包括剩余时间、任务进展和工具结果；行动包括继续工作、复查、休眠或提前结束。

## 核心方法

AgentTime 包含 222 个任务、18 个基准，目标时长从 1.25 分钟覆盖到 72 小时。每个任务—Agent 组合进行 3 次新运行。主实验比较 Claude Fable 5.1＋Claude Code、GPT-5.6 Sol＋Codex 和 GPT-6 Astra＋Codex，共分析 1,991 次有效运行；Fable 因 7 次拒绝而保留 659 次，另两种系统各 666 次。

时间控制用实际时长与目标时长的比值、±5% 准时率，以及对数—对数回归斜率衡量；斜率 1 表示目标时长扩大多少倍，实际时长也同比扩大。论文还做 Harness 交换、轨迹行为标注、任务得分比较、事前预测与事后回顾，从不同角度排除「只是某个 CLI 的计时问题」。

与固定 token 或静态超时基准不同，AgentTime 把时间作为 Agent 必须观察和控制的显式变量；与单纯的延迟测量不同，它检查 Agent 是否主动工作、反复复查或通过休眠对齐截止时间。

## 实验与证据

**准时率与尺度控制：**Fable 的 ±5% 准时率为 4%，实际／目标时长比为 2.86［2.68，2.99］，斜率 0.59［0.54，0.64］；Sol 分别为 39%、1.77［1.59，1.95］和 0.71；Astra 分别为 63%、1.18［1.11，1.25］和 0.94。区间来自论文表 3；Astra 接近线性控制，但不是完美计时器。

**同一任务内的响应：**控制任务差异后，Fable、Sol、Astra 的斜率分别为 0.24、0.58、0.90。目标时长扩大 16 倍时，实际时长平均只扩大 1.9、5.0、12.1 倍，说明较弱系统会忽略较长预算并提前停止。

**Harness 交换：**在 98 个任务上互换 Codex 与 Claude Code 后，模型差距仍存在。Astra 相对 Fable 的斜率优势在 Claude Code 中为 0.71，在 Codex 中为 0.69；单独更换 Harness 的影响约 0.14～0.16。证据支持「模型能力是主因之一」，但不能排除供应商服务差异。

**时间使用方式：**158 条可分类的 Astra 轨迹中，14 条休眠，占 9%；74 条反复检查，占 47%。在准时完成的 Agent 型任务子集中，只有 11／49 条在最后五分之一时段持续执行实质工作，24 条主要复查，14 条主要休眠。准时本身因此不能等同于有效利用预算。

**更久不一定更好：**最短与最长目标时限下的平均任务得分都在 62%～64%；只有 23%～25% 的任务在更长时限下得分提高。该结果反驳「只要给更多墙钟时间就能持续变好」的简单假设。

**预测与回顾：**222 个任务的事前预测中，Fable、Sol、Astra 高估时长的比例分别为 63%、83%、66%，典型误差为 2.6、3.8、2.9 倍；三者的预测中位数均为 15 分钟，而实际中位数分别为 13、6、10 分钟。23 个回顾任务中，保留原始计时线索时误差约 1.03～1.33 倍；清除计时线索后误差扩大到 2.58、5.38、2.62 倍，说明回顾更依赖轨迹中的显式时间提示。

**规模与成本：**研究合计 3,442 次 Agent 尝试，约 1,700 Agent 小时；作者按公开价格估算模型 API 约 86,000 美元，硬件约 7,000 美元，总计约 93,000 美元。

**本次核验：**本地固定到仓库 commit `b3491bb635e35ee7e3adf3ca8b214dbd25de1b31`，在独立虚拟环境运行测试，结果为 196 passed、22 skipped，用时 27.71 秒。这只证明已公开分析与工具代码的单元测试通过，不等于复现 1,991 次主实验。

## 局限与风险

**作者明确限制：**每个任务—时长设置只生成一次运行；只比较 3 个 Agent，且来自 2 个模型实验室；供应商负载、服务层计时和 Harness 开销会影响墙钟时间；指令措辞与最高推理档位固定。超过 8.3 小时的任务只有 4 个，72 小时端点的证据尤其稀疏。

**调研推断：**三次运行能缓解随机性，但对长尾服务波动仍不足。准时率的 ±5% 窗口对短任务非常严格，对长任务又可能容许较大的绝对误差，应与绝对分钟误差一起阅读。论文涉及的闭源模型和计费服务会持续变化，后续复跑可能与当前版本不完全可比。

公开数据采用 CC BY 4.0，代码采用 MIT；但 Hugging Face 轨迹集需要同意访问条件。论文称共有 8,911 条轨迹，其中主时间控制实验 1,991 次运行只有 777 条带完整轨迹。仓库 README 说明当前公开的 `forecasting/` 仍对应早期 235 题版本，论文主实验代码将后续补充，现阶段不能一键重建全部图表。

## 复现与应用

当前可复现的最低成本路径是运行仓库分析测试、检查公开结构化数据并重算斜率、准时率和置信区间。若要复现 Agent 行为，需要锁定模型快照、Harness 版本、地区与供应商服务条件，并保存服务器时间、工具时间和模型调用时间，避免把排队延迟误判为 Agent 决策。

产品侧不应只提供「最大运行时间」。更稳妥的接口应同时包含软截止时间、剩余预算观察、阶段检查点、最小有效工作要求与提前结束原因。对异步任务，可让 Agent 定期报告进度和剩余工作，而不是通过休眠填满时限。

## 相关工作

- **METR 长任务评测：**提供按人类完成时间组织的长程任务，AgentTime 继承其时长尺度并加入显式时间控制。
- **PostTrainBench：**提供更长的训练型任务，但 AgentTime 中超过 8.3 小时的样本主要集中于少数任务，仍是证据薄弱区。
- **RE-Bench：**关注机器学习研究工程能力；AgentTime 用其任务检查延长时间是否改善得分。
- **SWE-bench 系列：**提供软件修复任务，构成短到中等时长的时间控制场景。
- **Agent 运行时预测：**既有工作多预测成本或成功率，AgentTime 进一步检验 Agent 自己能否预测、控制和回顾墙钟时间。

## 调研判断

**阅读优先级：**高。时间控制是 Agent 编排、成本承诺和异步交付的基础能力，却长期缺少直接评测。

**可信度：**中高。任务覆盖、三次运行、Harness 交换和多层行为分析支撑主要结论；单次任务—时长运行、闭源服务波动和不完整主实验代码限制复现。

**适用对象：**Agent 平台、调度器、长程评测、成本与服务等级目标设计者。

**后续观察：**主实验代码是否完整公开；更多模型与本地推理系统是否复现斜率差异；如何区分有效工作、重复复查和等待；能否把时间预测误差纳入动态预算与中止策略。

## 结论摘要

- 动态并发不是默认加速器。在 354 个任务、3 个 Agent、并发与串行两种模式的 2,124 次执行中，并发通常增加 token 与运行时间，并在若干软件工程基准上显著降低成功率。
- 并发的收益随任务的可并行结构而变。LoopsBench 上三种 Agent 的平均测试通过率提高，而 RepoZero 上平均下降 8.29 个百分点；不能把「多开子 Agent」当作与任务无关的固定策略。
- 论文最重要的产出不只是排行榜，而是把失败归因到共享写入覆盖、依赖错序、主 Agent 过早收敛、子 Agent 结果未整合等并发机制。
- 开放工件覆盖全部 2,124 条轨迹并包含逐任务评测与部分人工注释，但仓库超过 2 GB、根目录缺少清晰的聚合入口，本次只核验样例与冻结结果，没有独立复跑商业模型实验。

## 研究问题与背景

长程编码 Agent 已能动态派生子 Agent。直觉认为，多路探索可以缩短墙钟时间并增加覆盖面；但真实编码任务包含共享文件、串行依赖、统一测试与最终整合，并发也会引入协调成本。论文要回答三个问题：并发是否提高任务成功率，是否真的更快，以及哪些交互机制决定收益或失败。

这里的 Agent 状态由主轨迹、工作区和子 Agent 返回结果共同构成；观察包括仓库、工具输出与子 Agent 消息；行动包括派生、继续或终止子 Agent，以及编辑、测试和提交代码。论文比较的是同一 Agent、同一模型、同一提示、同一环境与时间预算下的并发和串行执行，尽量把差异收敛到调度方式。

## 核心方法

实验覆盖 SWE-bench Verified 100 题、RepoZero 150 题、NL2Repo 26 题、ProgramBench 50 题和 LoopsBench 28 题，共 354 个不同任务。系统组合为 Codex＋GPT-5.4、Claude Code＋Claude Opus 5、Kimi Code＋Kimi K3；每个组合分别运行并发和串行模式，因此共有 2,124 次执行。

串行模式要求一个子 Agent 完成后才能启动下一个；并发模式允许动态重叠。作者统一模型、推理档位、提示、任务环境与时间预算，并记录成功、测试通过率、token、运行时间和执行轨迹。对 1,062 条并发轨迹进行人工审阅，保留 650 个可归因案例，标注 804 个模式实例，最终形成 4 类、13 个子类和 28 个具体模式。

与仅比较静态多 Agent 拓扑的工作不同，本研究观察 Agent 自己决定何时派生与整合子 Agent 的动态并发；与单纯的成功率评测不同，它同时检查成本、墙钟时间和轨迹级因果线索。

## 实验与证据

**总体效果：**SWE-bench Verified 上，Codex 的任务成功数从串行 71 提高到并发 71，实际持平；Claude 从 83 降到 59，Kimi 从 77 降到 59。经 Holm 校正的 McNemar 检验显示，Claude 的下降 p＝5.08348×10⁻⁷，Kimi 的下降 p＝0.0132176；Codex 的变化 p＝0.229481，不显著。

**任务结构差异：**跨三种 Agent，长程基准的平均测试通过率变化依次为 RepoZero −8.29 个百分点、NL2Repo −0.04 个百分点、ProgramBench ＋1.24 个百分点、LoopsBench ＋4.31 个百分点。LoopsBench 的任务成功数中，Codex 为 21.4→25，Claude 为 7.1→21.4，Kimi 为 25→25；方向说明可拆分循环更适合并发，但不能外推到一般仓库任务。

**成本与速度：**并发模式消耗串行模式 1.41～3.31 倍 token；15 个 Agent—基准组合中有 14 个运行时间增加。对两种模式都完成的 366 个任务，并发只在 102 个任务上更快，占 27.9%；若要求至少快 20% 且节省 60 秒，只有 46 个任务，占 12.6%。实验按公开 API 标价计算的总成本为 20,780.02 美元。

**失败机制：**轨迹审阅显示，常见问题包括多个子 Agent 修改同一文件导致覆盖、后续任务在前置结果就绪前启动、主 Agent 误把局部完成当作全局完成、子 Agent 输出未被验证或合并，以及过多并行探索挤占最终测试和修复时间。这些模式解释了为什么 token 增长不自动转化为成功率或墙钟收益。

**本次核验：**本地核对论文正文、表格与附录，并通过 GitHub API 固定到 commit `d7e7b399958616c8e8940505c0d09934c4b97cb7`。抽查 LoopsBench 的同一任务时，串行与并发目录均含评测摘要；并发轨迹的注释明确记录子 Agent 提前终止和执行错误。该核验确认工件与论文口径能对上，但不等于复现整体统计。

## 局限与风险

**作者明确限制：**结果只覆盖 3 个前沿 Agent 和 5 个编码基准；并发决策由特定 Harness 和模型共同产生，不能直接代表其他系统。轨迹级因果归因依赖人工判断，虽有分类规范，仍可能受标注者解释影响。

**调研推断：**统一墙钟预算并不能完全等价地控制供应商排队、缓存与工具服务波动。论文公开总成本，但没有把输入、输出、缓存和主／子 Agent token 细分到足以精确重算成本。GitHub 工件仓库公开但未检测到许可证，根目录也缺少易发现的聚合脚本入口，复用边界和复现实操成本仍高。

并发策略若直接进入生产编码链路，还需约束共享写入、依赖图、取消传播和最终所有权；否则「更多 Agent」会把逻辑错误变成调度错误，并放大成本。

## 复现与应用

适合的复现顺序是：先从公开轨迹重算每个任务的成功、测试、token 与运行时间；再用少量自有任务比较同一 Agent 的串行与并发；最后才扩展到付费全量运行。应同时保存调度事件、工作区 diff、子 Agent 返回值和最终测试，不能只记录最终答案。

工程应用不应默认开启最大并发。更合理的门控条件包括：子任务是否写入相互独立的文件、是否存在清晰的依赖图、合并结果能否自动验证、剩余墙钟时间是否足以整合。对于共享核心文件、串行调试或需要统一设计判断的任务，串行或受控小并发更稳健。

## 相关工作

- **SWE-bench Verified：**提供真实仓库修复任务，本论文把它作为并发与串行的共同评测场。
- **RepoZero：**强调从零理解与修改仓库；本论文中并发平均退化最明显，暴露共享上下文与协调问题。
- **NL2Repo：**从自然语言构建仓库级实现；并发总体接近持平。
- **ProgramBench：**检查更长程的程序合成；并发只取得小幅平均收益。
- **LoopsBench：**任务结构更容易拆分，本论文中并发收益最稳定，构成任务可并行性的正向对照。

## 调研判断

**阅读优先级：**高。它直接回答当前多 Agent 编码系统最容易被直觉误导的问题：何时并发、何时串行。

**可信度：**中高。受控配对、任务覆盖、统计检验、轨迹标注和公开工件共同支撑主要结论；但商业系统波动、人工归因和复现成本限制了外推。

**适用对象：**编码 Agent、任务编排器、工作区隔离和多 Agent 评测系统的设计者。

**后续观察：**是否补充许可证与聚合脚本；是否出现独立复跑；是否能训练或实现基于写集合、依赖图和剩余预算的动态并发门控；不同 Agent 之间的差异是否来自模型能力还是 Harness 调度。

## 结论摘要

1.  SafeActBench 不只检查最终状态是否正确，而是检查每个有外部影响的动作是否由 Agent 在动作发生前实际取得的证据支持，并核对后续动作是否使用了真实前序结果。
2.  基准包含 656 个案例、6 个业务域和 5 种协议，从静态判断、调查后不行动，逐步扩展到单动作、线性多动作和依赖图工作流；评分器完全确定性，不使用 LLM judge。
3.  10 个模型—Harness 组合在静态 Legacy 协议上最高接近 98%，但交互式 V1～V3 明显更低。V1 中，Agent 在证据不完整时提前行动的比例为 37.0%～66.9%；一旦证据完整，9／10 个组合的单动作成功率为 93.2%～100%。
4.  受控干预进一步表明，移除决定性记录后，Agent 仍在 46.5%～53.5% 的已完成 episode 中行动；相比缺失证据本身，用户声称「已经检查过」更能改变行动决策。
5.  阅读优先级高。论文把「正确结果」与「有证据支持的行动」分开，并公开案例、环境和评测器；但合成环境不能直接证明真实金融、医疗或基础设施部署安全。

## 研究问题与背景

工具型 Agent 会退款、修改配置、发送文件或控制设备。只看接口返回成功或最终状态正确，无法判断 Agent 是否在行动前核对了正确对象、当前状态、授权条件和依赖关系。一个 Agent 可能检查了订单 A，却对订单 B 执行退款；终态正确，但可观察轨迹没有支持这个动作。

论文把这一缺口定义为「证据—行动链」：每个后果性动作都必须由行动前已建立、且与正确实体和状态绑定的证据支持；多动作工作流还必须等待前序动作真实产生所需结果。研究问题因此从「动作是否成功」变成「Agent 是否先形成了足以支持动作的可核验证据」。

## 核心方法

**五级协议。**Legacy 只要求对固定候选动作给出 ALLOW／BLOCK／DEFER；V0 要求完成必要调查后不产生外部动作；V1 要求证据先于单一正确动作；V2 要求线性工作流中的后续动作使用真实前序结果；V3 允许任意合法拓扑顺序，但必须满足依赖图。

**Evidence Ledger。**评测器把观察绑定到来源交互、实体和状态。只有与目标动作对应的事实才算已建立；相同数值出现在其他实体上不能替代目标证据。多步任务中，前序动作的回执或确认状态进入后续动作的证据集合。

**确定性评分。**每个案例包含隐藏的证据要求、动作规格和依赖。评测器只读取任务上下文、实际工具轨迹和结果状态，检查调查完成度、工具、目标、参数、结果和依赖，不读取隐藏推理，也不调用 LLM judge。Exact Case Success 要求协议中的全部条件同时满足。

## 实验与证据

**覆盖范围。**656 个案例分布于客户与政策操作 112、工程与基础设施 109、法律与金融 144、研究辅助 97、智能家居 96、医疗操作 98；协议分布为 Legacy 86、V0 175、V1 131、V2 132、V3 132。5 个模型家族分别使用其原生 Harness 与统一 Inspect ReAct Harness，共 10 个组合；每个案例—组合运行 3 次，主评测覆盖率为 100%。

**主结果。**Claude-5／Claude Code 的总体 ECS 最高，为 67.2%；GLM-5.2／ZCode 在 Legacy 上为 97.7%，但 V1、V2、V3 仅为 32.1%、12.1%、34.1%。DeepSeek-V4／DSH 的相应三项约为 59%～65%，说明静态许可判断不能替代真实交互中的调查、时序与依赖执行。

**失败位置。**V0 中「完成必要调查前停止」为 21.7%～62.9%；V1 已尝试行动的 episode 中，「证据完整前行动」为 37.0%～66.9%。证据完整后的单动作成功率在 9／10 个组合中达到 93.2%～100%，表明主要瓶颈更常位于调查与行动时机，而不是工具调用本身。

**受控干预。**对 43 个 V1 案例移除一条决定性记录后，三个组合的行动概率下降 37.2～45.2 个百分点，但仍有 46.5%～53.5% 的已完成 episode 行动。向 Agent 提供用户侧「记录已经检查且满足条件」的声明，比仅呈现缺失证据更强地抑制行动，揭示模型对请求者措辞与可核验证据的权重失衡。

**评测器验证与本地检查。**656／656 个作者参考解通过评测器；120 个案例的盲审对行动支持判断达到 κ＝0.87；300 条模型轨迹审计中，误接受率为 2.0%，误拒绝率为 1.3%。本地固定 commit `841816cf1e376e6fbf8600cffac5df1736e1d369` 完成全部 Python 文件编译，并以无 API 模拟模式通过 SAB-V2-001；这验证公开运行入口，不等于重跑商业模型主评测。

## 局限与风险

**作者明确限制。**基准使用合成任务、虚构实体和受控策略，不能解释为真实金融、医疗、智能家居或基础设施系统的安全认证。证据账本描述可观察支持，而不是模型内部真正依赖了哪条证据；多动作协议上的证据干预仍留待后续研究。

**调研推断。**隐藏规格把「行动前必须知道什么」固化为作者定义，现实业务的政策冲突、权限委托和信息时效更复杂。原生 Harness 与 Inspect 的比较固定了案例，却仍混合了提示、工具呈现、运行时恢复和模型适配差异，不能把全部差值归因于单一 Harness 机制。

**干预边界。**请求者声明降低行动概率，不等于模型形成了正确证据观；不行动也可能是过度保守或运行失败。SCGR 分析中，结构化证据选择对部分组合有显著改善，对另一些组合反而下降，说明格式化证据本身不是通用修复。

## 复现与应用

公开仓库提供 656 个案例、6 个环境、工具 Schema、确定性评测器、模拟入口与 OpenRouter 运行入口。核心 runner 使用 Python 3.11 以上和标准库；代码采用 MIT，数据采用 CC BY 4.0。完整主表仍需要对应商业模型与 Harness，成本、版本和可用性会影响重跑。

工程应用可把 Evidence Ledger 机制放在外部写入、付款、权限修改和跨系统操作之前：记录目标实体、必要条件、证据来源、证据时间与前序结果；门禁检查缺失、错误实体和未完成依赖。它适合作为审计与阻断信号，不应单独替代领域策略或人工审批。

## 结论摘要

- 论文把库设计质量定义为下游 Agent 实际写出的程序是否正确且简单，而不是库自身是否能编译、是否通过内部测试，或人类是否喜欢其 API。这一评价对象更接近 Agent 互相继承代码的真实后果。
- LibraryDesignBench 覆盖 15 个库设计任务、4 种语言与 242 个专家验证问题。每个设计配置产生 3 个库，下游 3 个不同模型家族的实现 Agent 使用这些库，共形成每个设计配置 2,178 次评测。
- 最强 Opus 5.5 得分 48.9，略高于人类生产库的 46.6；但各设计器的测试通过率都在 84.1%～86.6%，主要差异来自下游程序复杂度，而不是正确率。
- Agent 在 15 个任务中的 11 个复现了人类生产库的主要抽象。对 810 个部分通过且代码偏长的样本审计显示，82% 的首要原因是库自身限制，其中 64% 属于接口僵硬或调用冗长，只有 14% 是能力缺失。
- 面向 Agent 的显式设计提示、可运行示例和子 Agent 测试把 GPT-6 Astra 得分从 44.1 提高到 46.4，但设计成本从 4.51 美元增至 8.24 美元；论文只评估组合干预，不能归因到单个组件。

## 研究问题与背景

现有 Coding Agent 评测通常判断实现是否通过测试，却很少问一个 Agent 生成的库是否能减少后续 Agent 的工作量。单测无法评价接口是否易发现、可组合或足够灵活；按预设签名评分又会把答案写进规范；人类评审则可能偏好对人类友好、但不一定适合模型检索和调用的 API。

论文因此把设计 Agent 和使用 Agent 分开。设计 Agent 只收到能力说明和少量使用情境，没有接口、方法签名或测试；使用 Agent 则在看不到隐藏测试的情况下，用该库解决真实编程问题。库的价值由下游程序的正确性与剩余代码复杂度决定。

## 核心方法

每个任务分为设计与评测两阶段。设计阶段要求 Agent 从开放规格实现完整库；评测阶段固定 3 个实现 Agent，分别使用设计出的库完成一组问题。基准涉及 Rust、Python、TypeScript 与 Haskell，覆盖 CLI 解析、数据框等 15 类库。

单个下游程序得分为测试通过率的平方乘以简单度。简单度由源代码行数、圈复杂度、认知复杂度和 Halstead Volume 四项相对专家参考实现的比值平均得到，每项上限为 1。平方项使正确性优先，同时避免用密集单行代码只优化行数。

生产库与无库是两个固定基线；设计器覆盖 9 个前沿模型的 11 个模型—Harness 配置。3 个实现 Agent 分别来自不同模型家族，所有条件使用同一批容器、问题、提示、格式化器和隐藏测试。任务等权，置信区间按任务层聚类近似。

## 实验与证据

Table 1 显示，Opus 5.5 得分 48.9［48.0, 49.9］，生产库为 46.6［46.1, 47.2］，无库为 34.4［33.9, 34.9］。DeepSeek V4 Pro 为 31.2，低于无库；Haskell 中约 70% 的「设计器×任务」组合低于无库，说明生成一个库可能让后续 Agent 更差。

各配置测试通过率仅在 84.1%～86.6% 之间，排名主要由简单度决定。生产库比无库高 12.3±0.4 分，但每个下游问题平均增加 0.14±0.02 美元成本。Opus 5.5 设计库的通过率与简单度分别为 86.6% 与 64.5；生产库为 85.4% 与 61.5。

失败审计抽取 6 个设计配置、共 810 个部分通过且代码长于参考的样本。82% 的首要问题来自库本身；接口僵硬和调用冗长合计 64%，覆盖缺失为 14%。另一个作者分析发现，180 个解答中人工标注的 13,562 行重实现代码，有 41% 在重复库已提供但隐藏、难用或失效的功能。

LibraryUseBench 固定使用生产库，发现能力更强的模型更会利用库。GPT-5.6 Luna 从低到高推理强度，测试通过率由 51.4% 增至 84.5%，读取的库文件从 2 个增至 15 个；更强提示主要把简单度从 48.7 提高到 60.4。最低限度提示下，24% 的运行从未打开库。

组合式 Agent-first 干预让 Astra 的设计分从 44.1 提高到 46.4，三个实现 Agent 均有提升，四种语言中三种提升；收益主要来自程序缩短。设计成本近乎翻倍，且没有逐项消融。

## 局限与风险

作者明确限制：15 个任务偏向存在成熟生产库和明显复用机会的工作负载；简单度指标只是 Agent 友好性的代理，未覆盖运行性能、长期维护、安全、版本兼容和人类可理解性。设计与使用阶段采用固定模型和 Harness，不能直接外推到其他提示、工具或模型版本。

调研推断：参考实现以人类生产库为基础，可能把既有 API 设计当作隐含尺度；四项静态复杂度与 Agent 的真实推理成本只有间接联系。最强结果高于生产库 2.3 分，但论文未直接报告两者的配对差值区间，不能据此宣称稳定超越。价格和模型版本也会漂移。

## 复现与应用

官方仓库公开任务、配置、运行器、结果处理与文档。本次在独立临时目录固定 commit `905bb62859cf5ae340562bf4bde6abfa1b9f5a41`，按仓库开发依赖运行测试：212 passed、8 skipped；跳过项均为需要显式启用的慢速端到端测试。未复跑每配置 2,178 次模型评测，也未验证费用账本。

工程上，库和工具接口评审可增加「下游 Agent 剩余工作量」指标：隐藏任务通过率、需要写的新代码、是否读取文档、是否重复实现已有能力、工具调用数与费用。设计提示可要求先写使用者程序、提供可运行示例并让子 Agent 试用，但应分开消融。

阅读优先级：很高，适合 Coding Agent、Agent 工具平台、SDK／API 设计、评测和长期代码维护团队。可信度：高但仍需外部复跑；受控两阶段设计、跨模型用户、真实生产库基线、任务聚类区间、开放代码和本地测试形成强证据。

加权评分为 95／100：Agent 相关性 5.0／5、研究贡献 4.9／5、实验证据 4.8／5、可复现性 4.8／5、新鲜度 5.0／5、可验证关注度 1.6／5。该分数满足滚动窗口第 10～12 篇的放宽门槛。

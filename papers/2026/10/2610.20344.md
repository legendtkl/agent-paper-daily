## 结论摘要

- Doc2Harness 不再把 Harness 当作固定评测条件，而是让模型根据规格从零构建完整 Coding Agent Harness，再单独评价这个工程产物。
- 冻结候选 Harness 后，由脚本化 mock model 驱动完整会话，并从模型请求、磁盘文件、进程退出码和命令输出四个外部通道判定；positive control 用于排除「功能没有运行」造成的空洞通过。
- 19 个模型各独立构建 3 次，在 328 个测试上的通过率从 27.44% 到 53.05%；即使最强模型也未通过近一半测试，Harness 构建仍是明确的能力缺口。
- 主榜、分类差异和三次重复支撑「当前模型难以稳定构建完整 Harness」；模块数与得分的负相关只是观察性线索，不能解释为因果。
- 官方仅公开 94 个场景，完整 328 个测试保留不公开；因此评测框架可运行，但论文主榜尚不能独立复现。

## 研究问题与背景

Coding Agent 的能力不仅来自模型，还取决于 Harness 如何管理交互循环、工具执行、权限、上下文、会话状态、失败恢复和结果验证。现有 SWE 基准通常固定 Harness，再根据下游任务是否解决评价模型；这种协议无法回答另一个问题：模型能否根据一份行为规格，构建一个完整、可工作的 Agent Harness。

这类任务也不同于普通仓库补丁。Harness 的同一功能可以有多种内部实现，且它本身不会完成下游任务，必须被一个模型驱动才能观察行为。如果直接接入真实模型，驱动模型的能力又会污染对 Harness 的判断。Doc2Harness 的目标是把「构建者」和「驱动者」分离，使 Harness 本身成为评测对象。

## 核心方法

## 两阶段隔离

**Stage 1：构建。**被测模型在固定的 OpenCode builder harness 中工作，输入包括一份 10 章开发文档和一个只声明 3 个不可变接口、约 70 行代码的骨架。开发文档合并并消歧 12 个前沿 Harness 的公开用户文档；模型在隔离容器中实现交互循环、工具、权限、会话等完整功能。每次构建最多 24 轮、2 小时墙钟时间和 3 次提交。

**Stage 2：评测。**候选 Harness 冻结后被复制到独立容器，每个测试使用独立 fixture，并由脚本化 mock model 按预设响应完成一次端到端会话。这样，测试期间变化的是 Harness，而不是驱动模型。

## 四通道判定与正向对照

每个测试从四类可观察结果取证：发送给模型的请求、磁盘文件、进程退出码和命令输出。仅依赖「禁止出现某效果」的测试可能在功能根本没有运行时误判为通过，因此 130／328 个测试由至少一个 positive control 门控。只有观测前提成立且目标断言成立，测试才记为通过。

## 测试来源

测试由三类来源交替补充：从 Claude Code、OpenCode、Gemini CLI、Kimi Code 的 21,083 个公开 issue 中筛选缺陷；比较候选 Harness 与成熟 Harness 的行为差异；从已有区分力测试做单变量扩展。该流程强调可观察行为，不要求候选复刻某个参考实现。

## 实验与证据

完整测试集包含 328 个测试，分布于权限 61、文件操作 75、会话状态 84、direct drive 33、headless 40、交互终端 20，以及 15 个工件、启动与扩展测试。论文评价 19 个前沿模型，每个模型独立构建 3 次，共 57 个候选 Harness。

GPT-6 Astra 的总体通过率为 53.05±0.25%，Hy3 为 27.44±0.43%，两者相差约 26 个百分点。权限类别的 strong-weak gap 最大，为 50.8 分；交互终端平均通过率已达 79.9%，接近饱和。56 个测试被全部候选 Harness 失败，16 个被全部通过，其余 256 个对模型具有区分力。

论文报告 KR-20 为 0.913，说明测试结果表现出较高内部一致性。但单变量扩展会产生相关测试，一个缺陷也可能同时导致多个测试失败，因此该指标不能解释为 328 次独立测量。

候选 Harness 的代码量跨模型差异较大。控制代码行数后，模块数与通过率的偏相关为 -0.423，留一模型检查范围为 -0.484～-0.309。该结果说明「功能拆分方式」值得进一步实验，但模型身份是明显混淆变量，现有数据不支持「减少模块会提高得分」的因果结论。

**本地核验：**官方仓库固定 commit 为 `5411f53d497a6c76c1dd41bd55f08cc033203d2b`。对 `src/` 与 `tools/` 下全部 Python 文件执行 `py_compile` 通过；目录完整性检查得到 94 个公开场景。未启动 Docker、未运行付费模型构建，也未重跑论文完整主实验。

## 局限与风险

**作者明确限制：**协议只评价一次构建，不包含根据行为反馈反复 build-evaluate-repair；每次构建最多 3 次形式检查提交，较早提交的模型分数可能是能力下界。单个缺陷可能让一组相关测试共同失败。

**调研判断：**Stage 2 对冻结 Harness 的判定可重复，但 Stage 1 的 LLM 构建仍具随机性，不宜把整套流程称为完全确定性。328 个断言没有通过参考 Harness 做外部有效性校准；positive control 只能证明观测前提成立，不能证明断言本身正确。开发文档来自公开 Harness 文档，模型可能已有训练语料熟悉度，论文没有量化重写后的残余重合。

每模型只有 3 次构建，中游模型的均值差距常小于构建间标准差，细粒度名次不稳定。完整测试集保留不公开，第三方无法核验 328 个断言、复现主榜或检查测试覆盖偏差。

## 复现与应用

官方仓库使用 Apache-2.0，要求 Python 3.11+ 和 Docker；Stage 2 只依赖 Python 标准库，不需要模型密钥。公开版本包含 94 个场景，其中 53 个计分测试、41 个 positive controls，完整目录加载时会校验 digest。Stage 1 需要官方 builder image、本地 LiteLLM gateway 和模型 API。

工程上最值得复用的是评测机制：冻结产物、用 mock model 驱动协议、从外部通道判定效果，并为否定性断言配置正向对照。它适用于权限、工具协议、会话状态、错误码和启动行为，但不能替代真实模型与真实工作负载的端到端效果评测。

复现主榜需要未公开的 275 个计分测试／控制组合、19 个模型的相同版本与调用配置，以及 Stage 1 模型成本。当前公开代码足以复核框架结构和 94 个场景，不足以验证论文全部数值。

## 相关工作

- [HarnessDev](https://arxiv.org/abs/2609.01437)：让模型创建并演化 Harness，但主要通过下游任务表现评价；Doc2Harness 改为直接检查冻结 Harness 的行为契约。
- [Rethinking the Evaluation of Harness Evolution for Agents](https://arxiv.org/abs/2607.12227)：讨论 Harness 演化评测的混淆；Doc2Harness 用固定 builder 和脚本化驱动进一步隔离构建能力。
- [EvoHarnessBench](https://arxiv.org/abs/2609.04280)：关注 Agent 是否能跟上持续变化的 Harness；Doc2Harness 关注从规格到完整 Harness 的一次性工程构建。
- [Auditing Agent Harness Safety](https://arxiv.org/abs/2605.14271)：评价既有 Harness 的安全属性；Doc2Harness 覆盖更广的工程契约，并把权限行为纳入主要类别。
- [Claw-SWE-Bench](https://arxiv.org/abs/2606.12344)：比较不同 Harness 对 Coding Agent 下游任务的影响；Doc2Harness 则直接评价 Harness 本体，二者分别回答「用起来怎样」与「构建得是否符合规格」。

## 调研判断

**阅读优先级：**高。论文把长期被当作隐含变量的 Harness 工程转化为可单独测量的对象，评测协议比榜单本身更值得复用。

**可信度：**中高。两阶段隔离、外部观测、正向对照、三次构建和类别分解共同支撑主结论；完整测试不公开、断言未做参考实现校准，以及架构相关性的混淆限制了更强解释。

**适用对象：**Coding Agent／通用 Agent 平台负责人、Agent 评测研究者、权限与工具协议设计者，以及需要区分「模型能力」和「Harness 能力」的团队。

**后续观察：**完整 328 个测试是否开放；是否加入参考 Harness 校准和人工断言审计；是否增加更多独立构建、模型版本控制和成本披露；是否评价基于行为反馈的迭代修复；模块组织结论能否通过同模型受控干预验证。

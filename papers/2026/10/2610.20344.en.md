## Conclusion summary

- Doc2Harness no longer regards Harness as a fixed evaluation condition, but allows the model to build a complete Coding Agent Harness from scratch according to the specifications, and then evaluates this engineering product separately.
- After freezing the candidate Harness, the scripted mock model drives the complete session and determines from four external channels: model request, disk file, process exit code and command output; positive control is used to eliminate hole passes caused by "the function is not running".
- 19 models were each built independently three times, with pass rates ranging from 27.44% to 53.05% on 328 tests; even the strongest model failed nearly half of the tests, and the Harness build was still a clear capability gap.
- The main list, classification differences and three repetitions support "the current model is difficult to stably construct a complete Harness"; the negative correlation between the number of modules and the score is only an observational clue and cannot be interpreted as cause and effect.
- Only 94 scenes are officially disclosed, and the complete 328 tests are kept private; therefore, the evaluation framework can be run, but the main list of the paper cannot be independently reproduced.

## Research question and background

Coding Agent capabilities come not only from the model, but also from how Harness manages interaction loops, tool execution, permissions, context, session state, failure recovery, and result validation. Existing SWE benchmarks usually fix the Harness and then evaluate the model based on whether the downstream tasks solve it; this protocol cannot answer another question: whether the model can build a complete and working Agent Harness based on a behavioral specification.

This type of task is also different from ordinary warehouse patches. The same functionality in Harness can have multiple internal implementations, and it does not complete downstream tasks by itself and must be driven by a model to observe behavior. If directly connected to the real model, the ability to drive the model will contaminate the judgment of Harness. The goal of Doc2Harness is to separate the "builders" from the "drivers" and make Harness itself the subject of evaluation.

## Method

## Two-stage isolation

**Stage 1: Build.** The model under test works in a fixed OpenCode builder harness, and the input includes a 10-chapter development document and a skeleton of about 70 lines of code that declares only 3 immutable interfaces. Development documentation merges and disambiguates public user documentation from 12 cutting-edge Harness; the model implements complete functionality such as interaction loops, tools, permissions, sessions, etc. in an isolated container. Maximum of 24 rounds, 2 hours of wall clock time, and 3 commits per build.

**Stage 2: Evaluation.** The candidate harness is frozen and copied to a separate container. Each test uses a separate fixture and completes an end-to-end session with a scripted mock model based on preset responses. This way, it is the Harness that changes during testing, not the driving model.

## Four-channel judgment and forward comparison

Each test draws evidence from four categories of observables: requests sent to the model, disk files, process exit codes, and command output. Tests that rely solely on "disabling an effect" may falsely pass when the function is not running at all, so 130/328 tests are gated by at least one positive control. The test is considered passed only if the observation premise is true and the target assertion is true.

## Test source

The test is alternately supplemented by three types of sources: screening defects from 21,083 public issues of Claude Code, OpenCode, Gemini CLI, and Kimi Code; comparing the behavioral differences between candidate Harness and mature Harness; and doing univariate expansion from existing discrimination tests. This process emphasizes observable behavior and does not require candidates to fork a reference implementation.

## Experiments and evidence

The complete test set contains 328 tests, distributed among permissions 61, file operations 75, session state 84, direct drive 33, headless 40, interactive terminal 20, and 15 artifact, startup and expansion tests. The paper evaluates 19 cutting-edge models, each model is independently built three times, resulting in a total of 57 candidate harnesses.

The overall pass rate of GPT-6 Astra is 53.05±0.25%, and that of Hy3 is 27.44±0.43%, with a difference of about 26 percentage points. The permission category has the largest strong-weak gap at 50.8 points; the average pass rate of interactive terminals has reached 79.9%, which is close to saturation. 56 tests were failed by all candidate Harness, 16 were passed by all, and the remaining 256 were discriminative for the model.

The paper reported that the KR-20 was 0.913, indicating that the test results showed high internal consistency. However, univariate expansion produces correlated tests, and a defect can cause multiple test failures simultaneously, so this metric cannot be interpreted as 328 independent measurements.

The code size of candidate Harness varies widely across models. After controlling the number of lines of code, the partial correlation between the number of modules and the pass rate is -0.423, and the leave-one-out model checking range is -0.484~-0.309. This result shows that the "functional split method" is worthy of further experimentation, but the model identity is an obvious confounding variable, and the existing data does not support the causal conclusion that "reducing modules will improve the score."

## Limitations and risks

**Explicit restrictions from the author:** The protocol only evaluates one build, and does not include repeated build-evaluate-repair based on behavioral feedback; each build has a maximum of 3 formal check submissions, and the model score of an earlier submission may be the lower bound of capability. A single defect can cause a group of related tests to collectively fail.

**Research Judgment:** The determination of frozen Harness in Stage 2 is repeatable, but the LLM construction in Stage 1 is still random, and it is not appropriate to call the entire process completely deterministic. 328 assertions have not been calibrated for external validity by reference to Harness; positive control can only prove that the observation premise is true, but cannot prove that the assertion itself is correct. The development documents come from public Harness documents. The model may already be familiar with the training corpus. The paper does not quantify the residual overlap after rewriting.

There are only 3 builds per model, the mean difference of mid-stream models is often smaller than the inter-build standard deviation, and the fine-grained rankings are unstable. The full test set remains private, and third parties cannot verify the 328 assertions, reproduce the master list, or check for test coverage deviations.

## Reproduction and applicationThe official repository uses Apache-2.0 and requires Python 3.11+ and Docker; Stage 2 only relies on the Python standard library and does not require a model key. The public version contains 94 scenarios, including 53 scoring tests, 41 positive controls, and the digest is verified when the full directory is loaded. Stage 1 requires the official builder image, local LiteLLM gateway and model API.

The most worthy of reuse in engineering is the evaluation mechanism: freezing products, using mock models to drive protocols, judging effects from external channels, and configuring positive controls for negative assertions. It applies to permissions, tool protocols, session states, error codes, and startup behaviors, but it cannot replace end-to-end performance evaluation of real models and real workloads.

Reproducing the master list requires an undisclosed 275 scored test/control combinations, identical versions and calling configurations of 19 models, and Stage 1 model costs. The current public code is enough to review the framework structure and 94 scenarios, but not enough to verify all the values ​​of the paper.

## Related work

- [HarnessDev](https://arxiv.org/abs/2609.01437): Let the model create and evolve Harness, but mainly through downstream task performance evaluation; Doc2Harness instead directly checks the behavioral contract of frozen Harness.
- [Rethinking the Evaluation of Harness Evolution for Agents](https://arxiv.org/abs/2607.12227): Discusses the confusion of Harness Evolution evaluation; Doc2Harness further isolates build capabilities with fixed builders and scripted drivers.
- [EvoHarnessBench](https://arxiv.org/abs/2609.04280): Focus on whether the Agent can keep up with the continuously changing Harness; Doc2Harness focuses on one-time engineering builds from specifications to complete Harness.
- [Auditing Agent Harness Safety](https://arxiv.org/abs/2605.14271): Evaluate the safety attributes of existing Harness; Doc2Harness covers a wider range of engineering contracts and incorporates authority behaviors into main categories.
- [Claw-SWE-Bench](https://arxiv.org/abs/2606.12344): Compares the impact of different Harness on the downstream tasks of the Coding Agent; Doc2Harness directly evaluates the Harness ontology, and the two answer respectively "how does it work" and "whether the construction meets the specifications."

## Research judgment

**Reading Priority:** High. The paper transforms the Harness project, which has long been regarded as a hidden variable, into an individually measurable object. The evaluation protocol is more worthy of reuse than the list itself.

**Confidence:** Medium to high. Two-stage isolation, external observation, forward comparison, three-dimensional construction and category decomposition jointly support the main conclusion; the complete test is not public, the assertion is not calibrated with reference implementation, and the confusion of architectural correlation limits stronger interpretation.

**Applicable objects:**Coding Agent/general Agent platform leaders, Agent evaluation researchers, permission and tool protocol designers, and teams that need to distinguish between "model capabilities" and "Harness capabilities".

**Follow-up observations:** Whether the complete 328 tests are open; whether to add reference Harness calibration and manual assertion audit; whether to add more independent builds, model version control and cost disclosure; whether to evaluate iterative repairs based on behavioral feedback; whether the module organization conclusions can be verified through controlled intervention with the same model.

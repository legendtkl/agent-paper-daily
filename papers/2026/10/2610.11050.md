## 结论摘要

1.  论文把评测对象从「最终界面看起来是否完成」推进到「一条 100～300 多步的轨迹是否严格满足原指令」。1,373 条任务由 523 个正例和 850 个指令互换负例组成，负例仍是连贯、完整的执行，只是完成了相近但不兼容的请求。
2.  在最难的 528 项 AH 子集上，最佳 GPT-5.5＋Codex Judge 的 balanced accuracy 为 80.9%；约每 5 个判断仍有 1 个错误。最强开源 Agent Judge 为 Qwen 3.6 27B＋OpenCode，得分 70.4%。
3.  工具调用不是稳定增益。GPT-5.5 从直接判断的 68.6% 提高到 Codex 的 80.9%，但 Qwen 3.6 27B 从直接判断的 77.6% 降到 OpenCode 的 70.4%。模型与 Harness 必须作为一个整体报告。
4.  最难发现的是「已完成目标但做了额外危险动作」。最佳 Judge 对 Bad Side Effect 的精确召回仍只有 24.1%，说明训练数据过滤、自动验收和奖励模型都可能把表面完整的违规轨迹当成成功。
5.  结论可信度为中高：配对设计、固定分母、跨模型／Harness 对照、消融和公开工件较完整；但标签没有独立人类一致性测量，正例审核计数在论文正文中存在一处需要澄清的叙述，不能把 80.9% 当作跨任务、跨版本的稳定上限。

## 研究问题与背景

长程 Computer Use Agent 的结果往往不能只靠最终 URL、数据库字段或文件内容判断。轨迹可能正确创建文件、发布页面并完成大部分步骤，却在某一步选错目标、遗漏约束，或执行了未经请求的外部动作。人工复查数百张截图和动作记录成本高，因此训练与评测逐步使用 LLM Judge；问题是这些 Judge 是否真的能找到决定成败的证据。

论文把问题限定为：给定用户指令、截图和动作序列，Judge 能否区分「完成了原请求」与「完整完成了一个非常相似但不兼容的请求」。这个限定避开了明显崩溃、循环和停滞，把难度集中在指令—轨迹一致性上。

## 核心方法

**配对构造。**标注人员为同一软件组合设计两个仅有细微差别的任务 A／B，并分别录制成功轨迹。A＋轨迹 A、B＋轨迹 B 是候选正例；A＋轨迹 B、B＋轨迹 A 是负例。互换后的轨迹仍然连贯，因此 Judge 不能靠「是否看起来完成」取巧。

**三类错误。**Critical Mistake 表示核心动作或目标未完成；Bad Side Effect 表示目标完成但产生额外成本、风险或暴露；Misunderstanding 表示局部参数或约束理解错误，短修正即可恢复。850 个互换负例中 844 个获得错误类型，6 个保留为无类型负例。

**三种数据划分。**AH-D 用于开发；AH 是由 3 个强开源模型共同筛出的困难集；AH-S 是较简单补集。分组以指令对为单位，避免同一对落入不同集合。

**两种 Judge 形态。**直接 Judge 在单次请求中接收完整轨迹；Agentic Judge 通过 Claude Code、Codex、Gemini CLI、OpenHands 或 OpenCode 选择证据并检查截图。主指标为 balanced accuracy，同时报告正例／负例准确率、错误类型召回、成本和耗时；缺失、解析失败、非布尔输出都计错。

## 实验与证据

**规模。**850 条人工演示经过审核形成 523 个正例，再与 850 个互换负例组成 1,373 项；平均约 136 步，覆盖 3 个操作系统、6 个领域和 323 种应用组合。录制共 166 小时，供应商报告的标注与复核投入为 6,077.5 小时。

**主要结果。**AH 的 528 项中，GPT-5.5＋Codex 为 80.9%，Gemini 3.1 Pro＋Gemini CLI 为 77.7%，Claude Opus 4.7＋Claude Code 为 76.0%。GPT-5.5＋Codex 的正例准确率为 71.8%，负例准确率为 90.0%，说明同一个综合分仍可能掩盖不同的误拒绝／漏放结构。

**Harness 效应。**GPT-5.5 使用 Codex 比直接 Judge 高 12.3 个百分点；Qwen 3.6 27B 使用 OpenCode 反而低 7.2 个百分点。在相同 AH 项和相同提示下，GPT-5.5 从 Codex 换到 OpenCode 会下降 3.7 个百分点。论文没有把这个差异归因到单一工具，因为截图选择、上下文管理与重试策略同时变化。

**消融。**移除指令后 balanced accuracy 约为 49.0%；只保留最终截图且移除动作记录时为 49.1%；保留指令和动作但移除截图时为 57.7%。这说明判定需要同时知道「用户要什么」和「实际发生了什么」。

**原文关键截图。**下图来自论文 Figure 2、第 3 页。它展示一条 195 步 NetBeans＋WordPress 轨迹：Claude Opus 4.7 看到内容、标签和发布动作都完成，仍漏掉了未经请求加入并发布 changelog 内容的 Bad Side Effect。截图支持「表面一致性会掩盖指令违例」这一结论；它只是单个案例，不能替代 1,373 项汇总统计。

## 局限与风险

**作者明确限制。**配对设计只覆盖相近指令之间的细微错配，不代表循环、崩溃、停滞和渐进漂移等完整失败分布。困难集依赖具体模型、提供方和版本；AH-D 之前的试验接触限制了「完全未见」声明。语料仅为英文，覆盖有限应用与 3 个操作系统，Judge 只能看到截图和动作记录，不等同于完整应用状态。

**标签可靠性。**论文没有收集独立标注人员之间的一致性。仓库补充材料报告后续错误类型复查与最终标签的 Cohen’s κ 为 0.802～0.810，但这反映不同审核阶段的一致性，不是独立人类复标。模型化残余 QA 在 156 项中确认 18 项，11.5% 的结果也不能解释为人类验证错误率。

**计数叙述。**Pith 的 T0 AI 评审指出，论文 Section 3.2 对候选正例的叙述未明确写出 388 项直接通过与 462 项进入仲裁的中间层。公开仓库的 stage-by-stage 文档已给出 388＋135＝523，但论文正文仍应澄清流程。该问题更像审计轨迹不完整，而不是推翻 523 这一最终分母；最终分母同时由三类划分 62＋227＋234 交叉验证。

**调研推断。**榜单为单次 Judge—Harness 运行的点估计，论文未给置信区间。模型与 Harness 更新很快，80.9% 不能外推为长期能力上限。数据和仓库当前均未声明许可证，限制了商业复用与再分发判断。

## 复现与应用

**公开工件。**GitHub 仓库固定到 commit `8584a347370ab1d92b908732cfabe72b3a23486d`，提供提示、Judge 实现、轨迹转换、评测、聚合脚本和构造说明；Hugging Face 数据集固定到 commit `c9fcd9fd857657cb86ae2b3cc35ea2271889bec1`。本地对仓库全部 Python 文件执行语法编译通过，并验证评测与分析 CLI 能正常加载。

**未完成的复现。**没有下载包含截图的完整数据，也没有重跑 11 个模型、5 种 Harness 的商业模型评测。README 估算 Claude Opus 全量 1,373 条约 140 美元、6 小时；该估算不是本轮实测。公开 CLI 的部分帮助文本仍保留 1,700 条构造池口径，而 README 和发布数据使用 1,373 条审核后口径，复跑时应以版本化 manifest 为准。

**应用建议。**适合用于自动验收、训练轨迹过滤、Computer Use Judge 选型和 Harness 对比。生产使用时至少分别报告正例与负例准确率，并把 Bad Side Effect 设为独立门禁；balanced accuracy 不能表达一次误放敏感动作与一次误拒绝普通任务的不同成本。

## 调研判断

**阅读优先级：**高。它直接回答自动 Judge 能否可靠验收长程 Agent，并把「任务看似完成」与「严格满足指令」分开。

**可信度：**中高。公开数据、脚本、固定分母、消融和跨 Harness 对照较完整；标签独立性、一次性运行、不确定性和许可证仍是主要缺口。

**适用对象：**Computer Use Agent、Agent 训练数据管线、自动评测与安全验收的研究和工程团队。

**后续观察：**独立人类复标是否改变 headline；作者是否修正文中计数叙述；数据与代码是否补充许可证；同模型同 Harness 内的截图选择与上下文管理消融；不同版本 Judge 的重复运行方差。

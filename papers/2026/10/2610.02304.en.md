## Research question and background

Simulink has been generated to evaluate whether multiple check files can be formed, whether the model can be executed, or whether the structure is close to a single reference implementation. These conditions fail to answer the more critical question: whether the candidate model meets engineering requirements in terms of boundary conditions, faults, transient processes, and causal mechanisms. SimuVerity therefore defines tasks as "building to specifications", allowing different modules, levels and layouts, and only using requirements and operational evidence to judge the results.

## Method

The benchmark covers 10 fields including power electronics and control, machinery, robotics, heat, fluids, automobiles, batteries, aerospace, communications and biomedicine, with 9 to 11 tasks in each field, for a total of 101 tasks. Domain experts first implement and repair the reference system to form an executable system portrait, and then write public specifications and four types of hidden tests based on it: work interval, interaction and failure, time process, mechanism and causality check.

The evaluation first goes through three gates: product delivery, native executability, and project qualification. After passing, it will be scored according to six dimensions: accuracy A, output quality Q, mechanism fidelity M, control and causal integrity C, working domain robustness R, and dynamic response and recovery D. Rather than scoring based on similarity to a reference structure, this process allows for multiple valid implementations while identifying "similar-looking but engineering-failed" candidates.

## Experiments and evidence

The paper compares 6 Agent systems. All systems used the same 101 public task specifications, delivery rules, workspaces, and MATLAB/Simulink environments; each task-system combination was run three times from independent sessions, for a total of 1,818 formal builds, using frozen task-level scorers.

| Agent system | Total score | Delivery rate | Execution rate | Engineering qualification pass rate |
|----------------------------------|-------|--------|----------|----------------|
| Opus 4.8 + Claude Code | 42.86 | 94.72% | 86.47% | 76.90% |
| GPT-5.5 + Codex | 41.72 | 98.68% | 94.72% | 75.58% |
| DeepSeek-V4-Pro + Claude Code | 28.40 | 97.03% | 88.12% | 61.39% |
| Qwen3.8-Max + Claude Code | 25.01 | 89.77% | 80.86% | 53.80% |
| GLM-5.3-Flash + Claude Code | 4.98 | 96.04% | 48.18% | 13.20% |
| Qwen3.8-27B-FP8 + Claude Code | 1.60 | 30.36% | 13.53% | 6.27% |

Structural analysis covers 95 candidates delivered by the first run of Opus. The end-to-end average scores for the three groups of reference consistent, partially similar, and different structures are 52.13, 44.05, and 42.37 respectively; looking only at the candidates who passed the engineering qualification, the average scores are 59.80, 52.61, and 61.20. 12 of the 24 top quartile candidates are not reference consistent structures, and there are still 7 zero-score candidates in the reference consistent group, 2 of which passed the qualification threshold.

Tool ablation only selects 10 tasks with strong performance under the complete tool condition, and cannot be extrapolated to the average tool effect of all 101 tasks; however, the single-factor control direction is clear: the total scores of Full MCP, No-Simulation MCP, and Batch-only are 78.46, 7.88, and 18.23 respectively.

## Limitations and risks

- The author does not list a separate "Limitations" chapter; it can be confirmed from the scope of experiments that the benchmark only covers Simulink and 10 engineering areas, and cannot be directly extrapolated to CAD, Modelica, software patches or real-world control systems.
- Research judgment: Scorers and system portraits are defined by reference systems and experts. Although structural diversity is allowed, thresholds, coverage, and domain assumptions may still miss alternative mechanisms or realistic working conditions.
- The six systems share the MATLAB MCP core tools, but the underlying model and Agent Harness are not completely orthogonal; the list reflects the model, Harness and tool adaptation at the same time and should not be interpreted as a pure model ranking.
- Ablation only covers 10 pre-selected strong tasks, and there is a conditional sample bias; it proves the importance of the tool in being able to complete the task, and does not prove that all tasks have the same magnitude.
- Complete reproduction requires MATLAB/Simulink product and task-specific components. Open code does not eliminate the cost of commercial licenses, licensing of third-party assets, and approximately 1,818 model runs.

## Reproduction and application

The repository provides public specifications, system portraits, native simulation scenarios, scorers, reference assets or imported recipes for 101 tasks, and frozen results from triplicates of six systems. First-party code and results are Apache-2.0, third-party assets are licensed separately. Reproducing the complete list requires Python 3.11, MATLAB/Simulink, the corresponding toolbox, MATLAB MCP, Claude Code or Codex, and the model version used in the paper.

This time, the public result verification script was run on fixed commit 28159c312e68, confirming 9 sets of experiments, 27 repetitions, 636 parent records, and 1,908 duplicate records; all 37 unit tests passed. This only verifies the format, aggregation, and internal constraints of the result package, and is not equivalent to independently rerunning the Agent or proving that the task scorer covers real-world engineering requirements.

## Related work- [SimuAgent/SimuBench](https://arxiv.org/abs/2601.05187): Cross-domain text-to-model generation, mainly checking basic execution, completeness and reference similarity; SimuVerity uses demand-level native simulation instead.
- [SimuGen](https://arxiv.org/abs/2506.15695): Reconstruct block diagrams from images and do basic execution checks; this paper focuses on text specifications and engineering performance.
- [ASWE-Bench related automotive multi-agent work](https://doi.org/10.1109/ACCESS.2026.3711515): Use boundary and time series testing in automotive control logic; SimuVerity is expanded to 10 fields and six-dimensional diagnosis.
- [StructureClaw](https://arxiv.org/abs/2607.14896): Emphasizes the traceable Agent and executable evaluation of structural engineering workflow; together with this paper, it embodies the shift from text answers to engineering artifacts and operational evidence.
- [Establishing Best Practices for Building Rigorous Agentic Benchmarks](https://arxiv.org/abs/2507.02825): Provides Agent benchmark design principles; SimuVerity implements independent workspaces, repeated runs, frozen scorers, and artifact release.

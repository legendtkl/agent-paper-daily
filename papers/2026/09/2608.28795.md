## 结论摘要

- 论文以 6 个模型、8 种工具配置和 1,116 次 Web 应用构建，受控测量 Coding Agent 的「验证表面」怎样影响启动、功能、界面质量和 token 成本。
- 最便宜的启动探针把启动率从 86.5% 提高到 99.5%，并取得大部分功能收益；完整 shell 相对无验证消耗 2.35 倍 token，但追加收益主要集中在并发、重启和排序等可执行压力测试。
- 截图只在错误可见时可能继续提高质量；相对 shell 的视觉收益未通过 6 项假设的多重比较校正，不能写成已确立结论。
- 核心判断是「工具只有覆盖真实失败方式时才有价值」。实验设计和统计报告较扎实，但单一人工评分者、被动截图工具、6 个独立模型块和任务范围限制外推。

## 研究问题与背景

Coding Agent 可以获得 linter、启动探针、shell 和截图工具，但现有工作通常比较整套外壳，难以把结果归因到某一种验证能力。论文将验证表面定义为 Agent 检查自身产物的工具集合，研究每增加一层能力能买到哪种质量、需要多少 token，以及收益是否与工具可观察的失败类型一致。

## 核心方法

作者构建最小 Coding Agent，固定系统提示、任务、基础文件工具和控制循环，只改变验证工具。5 个核心条件依次为无验证、仅 linter、仅启动探针、完整 shell、shell 加截图；另有 3 个定向条件分离视觉、延迟验证和自编测试。6 个模型各完成 7 类 Web 应用，每个组合重复 4～5 次，共 1,116 次独立运行。

结果从三个表面衡量：应用能否启动、API 自动压力探针的功能得分、盲条件人工评分的界面质量。论文预先固定 6 个主要假设，使用模型内差值、10,000 次置换、分层 bootstrap 和 Holm 多重比较校正，并用混合效应回归交叉检查。人工评分按冻结 rubric 随机顺序完成，4 周后重评 10% 样本，项目判定一致率为 98.8%，加权 κ 为 0.97。

与 SWE-bench、WebGen-Bench 等整体系统评测相比，本工作不比较 Agent 排名，而是测量工具能力的增量因果效应。与自调试和视觉反馈工作相比，它同时包含 API、视觉、性能和 brownfield 任务，用于定位「看得到」与「测得到」的边界。

## 实验与证据

**启动：**无验证条件为 86.5%（166／192），仅 linter 为 84.4%（162／192），启动探针为 99.5%（191／192），shell 为 99.0%（190／192），视觉条件为 99.4%（173／174）。启动探针相对无验证提高 13 个百分点，95% CI 为 +10～+16，Holm 校正后 p\<.001。

**功能：**3 个 API 可探测新建任务的均分依次为 81.9、78.3、91.7、94.2、92.6。shell 相对无验证提高 12.3 分，95% CI 为 +7.0～+17.5，校正后 p\<.001；其中约 10 分已经由启动探针取得。shell 的额外收益主要来自并发请求、进程重启和负载下排序。

**界面：**两个视觉困难任务的人评均分为 72.8、72.6、89.5、89.2、96.1。截图相对 shell 的差异方向为正，但主要假设校正后不显著；论文将其标为提示性证据。截图无法点击、输入、拖拽、悬停或调整窗口，因此该条件只测量被动视觉。

**成本：**启动探针约使用完整 shell 的 35% token，并比无工具构建还便宜；完整 shell 的 token 成本是无验证的 2.35 倍。作者解释为早期可执行反馈减少了盲目继续编写，而完整 shell 会引出更长的调试循环。

**负结果：**仅 linter 在启动和功能上均与无验证无显著差异，且 10 个无法渲染的前端解析错误中有 5 个出现在 linter 条件。一个定向自编测试条件在相关任务上提前停止，自己的测试通过，但自动行为得分更差，说明自写测试会重复 Agent 对任务的误解。

## 局限与风险

**作者明确限制：**截图工具是被动渲染器，不能发现点击后才出现的错误；模型推理内容未跨轮保留，限制了对支持持续 reasoning 外壳的外推。人工界面分数来自单一评分者，重评只证明稳定性，不证明正确性；3 个任务没有自动功能测试，可能高估「界面存在但数据为空」的应用。

统计强度主要来自 6 个模型，而不是每格 4～5 次高度相关的重复；单模型效应只能描述，不能独立显著。6 个预设效应中有 2 个在未校正时显著、校正后不显著，brownfield 结果的置信区间较宽。3 个模型的 API 拒绝指定采样参数，只能使用供应商默认值，但模型内条件保持一致。

**调研推断：**任务是 7 类 Web 应用，不覆盖大型仓库、长周期维护或真实 CI。启动探针的高收益不能直接推广为「任何 Coding Agent 只需要 smoke test」；正确结论是先覆盖最常见、最便宜验证的失败表面，再按风险增加更深验证。

## 复现与应用

论文称 Zenodo 归档包含 1,116 个最终应用、完整工具调用日志、机器评分、盲评 rubric、失败分类、3 个 SHA256 密封快照、预注册统计计划和分析代码，许可证为 CC BY-NC-ND 4.0。论文列出的 GitHub 仓库在 2026-09-02 返回 404，因此当前只能从 DOI 入口核验归档，复现可达性低于论文声明。

对工程团队，最可执行的策略是先统计失败类型，再为高频故障配置最低成本探针：启动与健康检查覆盖部署生存，集成测试覆盖并发和持久化，交互式浏览器覆盖点击、拖拽和响应式布局。验证工具数量本身不是目标，覆盖实际故障才是。

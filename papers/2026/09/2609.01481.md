## 结论摘要

- HoH 在固定 Coding Agent 外层加入「规划—开发—独立测试」循环，并把软件工件与经过测试的证据作为跨轮状态；贡献重点是长周期控制协议，不是新模型。
- 在 GameCraft-Bench、FrontierSWE 和 ProgramBench 上，3 个 harness–model 组合的 HoH@3 均优于对应单轮 Vanilla；作者报告平均相对提升 52.25%，最大相对提升 82.86%。
- 预算对照显示收益不只是多运行几轮：Codex + GPT-5.5 在 GameCraft-Bench 上，HoH@3 以平均每任务 8.41M tokens 得到 71.52 分，3 轮 Vanilla Continuation 以 6.33M tokens 得到 58.24 分；HoH@2 以 5.67M tokens 也高于后者。
- 证据边界明显：每个任务—条件只有 1 次有效生成，模型无统一可复现采样种子，70 轮游戏属于案例研究；官方仓库尚未公开核心实现，因此结果暂不能视为独立复现。

## 研究问题与背景

现有 Coding Agent 多在一次有界会话中完成局部修复。跨天构建完整软件时，代码只记录「当前是什么」，无法完整保留「为什么这样改、哪些失败未解决、哪些行为已经验证」。长轨迹还会带来重复检查、局部修复覆盖已验证能力，以及在证据不足时过早宣布完成。

论文把问题定义为：在模型与底层 harness 固定的情况下，如何让 Agent 从高层需求出发，持续扩展同一个软件工件，同时保留可验证进度、显式处理回归，并避免把实现者的完成声明当作验收结果。

## 核心方法

每轮包含三个相互分离的角色。Project Planner 读取全局需求、当前只读工件和上一轮证据，选择一个范围有限但局部完整的增量；Developer 是唯一写入者，基于上一轮工件实现增量并执行局部测试；QA Tester 在冻结的只读候选上执行黑盒与白盒检查，形成下一轮可消费的证据。

跨轮状态分为两类：工件状态保存代码、配置、资源与项目元数据；证据状态保存已验证行为、未支持主张、未解决失败和回归记录。运行时固定角色输入、权限和结构化交付物，并让不符合 Schema 的结果重试。详细计划、报告和历史保存在文件系统中，先暴露紧凑索引，需要时再按需读取。

与 AutoHarness、Meta-Harness 和 Self-Harness 直接修改 harness 不同，HoH 固定模型与底层 harness，优化的是同一软件项目在多轮规划、实现和验收之间的控制结构。与 MetaGPT、ChatDev 的预定义角色流程相比，HoH 更强调跨轮证据、冻结候选和独立接受条件。

## 实验与证据

**数据集与配置。**GameCraft-Bench 使用 45 个分层抽样任务，覆盖 15 个游戏家族；FrontierSWE 使用 17 个任务中的 15 个，其中包括 4 个实现、9 个性能和 2 个研究任务；ProgramBench 测试只给编译后可执行文件与文档的 clean-room 程序重建。三组配置分别为 Codex CLI 0.142.5 + GPT-5.5（high）、OpenCode 1.14.30 + DeepSeek-V4-Pro，以及 Pi 0.80.10 + MiniMax-M3。

**主要结果。**GameCraft-Bench 的平均总分从 Vanilla 到 HoH@3 分别为 49.58→71.52、26.90→48.98、42.16→58.78。FrontierSWE 平均奖励分别为 0.31→0.54、0.23→0.31、0.26→0.55；ProgramBench 平均测试通过率分别为 60.41→66.50、45.27→57.56、35.83→52.68。作者还在 Codex + GPT-5.5 上把 FrontierSWE 运行到 10 轮，Dominance 从 Vanilla 的 27.33% 提高到 HoH@10 的 72.67%，但该指标依赖论文定义的 11 个对手配置池。

**预算对照。**在 GameCraft-Bench 上，1／2／3 个开发 pass 的 Vanilla 分别为 49.58／54.99／58.24，HoH 分别为 59.71／64.84／71.52。HoH@2 使用 5.67M tokens，少于 3 轮 Vanilla 的 6.33M tokens，分数仍高 6.60 分。不同提供商的缓存计费口径不一致，因此 token 只能在同一配置内比较。

**消融。**完整 HoH@3 为 71.52 分；不更新计划、不回传证据、不 warm-start 分别降至 63.39、65.23 和 63.67。最后一种还把平均 token 提高到 11.12M，支持「保留工件状态与验证证据共同起作用」的机制解释。

**统计可靠性。**论文为 GameCraft-Bench 报告 95% bootstrap 置信区间，并公开逐任务分数；但每个任务—条件仅运行 1 次，客户端不提供统一生成种子，聚合结果无法分离随机生成方差。基础比较是单轮 Vanilla 对 3 轮 HoH，预算对照缓解但没有完全消除计算量与协议复杂度差异。

## 局限与风险

**作者明确披露。**由于算力限制，FrontierSWE 只使用 15／17 个任务；不同模型供应商的缓存 token 口径不同；生成温度与 top-p 使用各客户端默认值，无法设置共同随机种子。70 轮 FPS 游戏的验收范围包含运行、输入、音频与 3D 资源检查，但仍是单一项目案例。

**调研推断。**Planner、Developer 与 Tester 使用同一 harness–model 配置，角色隔离能降低自证风险，却不能提供真正独立模型的审查。QA 证据本身会进入下一轮，因此若测试标准遗漏需求，循环可能稳定优化错误目标。官方仓库目前只有论文素材和演示，没有 HoH-lite 或完整基准执行代码，复现门槛高于论文文字呈现。

## 复现与应用

论文附录给出角色协议、任务样本、执行环境、预算定义、逐任务结果与消融设置。复现至少需要对应 harness 与模型访问、GameCraft-Bench／FrontierSWE／ProgramBench 环境、Godot 4.6.2、Docker，以及每任务数百万 token 的推理预算。FrontierSWE 中部分任务需要 NVIDIA H200；多日 FPS 案例使用 Godot 4.7 和专用 MCP、素材与测试 Skill。

工程上最可迁移的部分是：限制单轮变更面、分离唯一写入者与只读验收者、把验证结果作为版本化项目状态、对每个候选绑定证据，以及显式保留回归历史。这些原则可在不复制全部三角色框架的情况下用于长周期 Coding Agent。

## 相关工作

- [Agentic Harness Engineering](https://arxiv.org/abs/2604.25850)：把工具、中间件和长期记忆作为 harness 能力来源；HoH 更关注固定 harness 之上的跨轮软件演化。
- [Meta-Harness](https://arxiv.org/abs/2603.28052)：搜索与改进 harness 代码；HoH 不修改底层 harness，而是优化项目级规划、开发与验收循环。
- [GameCraft-Bench](https://arxiv.org/abs/2606.17861)：HoH 的三项主评测之一，为完整可玩游戏提供运行与质量评分。
- [Recursive Agent Harnesses](https://arxiv.org/abs/2606.13643)：同样研究固定基座模型下的递归 harness 收益，可用于判断 HoH 的增益是否来自外层控制结构。
- [MetaGPT](https://arxiv.org/abs/2308.00352)：使用预定义角色和工件执行软件开发；HoH 增加跨轮证据状态、冻结候选与独立 QA。

## 调研判断

**阅读优先级：**高。适合负责 Coding Agent 编排、长任务状态、验收机制和工程评测的研究者与技术负责人。

**可信度：**中高。跨三个基准、三个 harness–model 组合、预算对照、消融和逐任务结果形成较完整的内部证据；单次生成与核心实现未公开显著限制外部可信度。

**后续观察：**HoH-lite 与基准脚本是否公开；独立团队能否在相同 pass 和 dollar 预算下复现；跨语言、已有大型仓库与真实 CI 约束是否仍有收益；长期循环中的安全边界、回滚频率和人工接管成本。

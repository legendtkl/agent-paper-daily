## 结论摘要

- MaxKernel 把 TPU 内核开发拆成规划、实现、编译修复、测试、自动调优和 XProf 分析等专门 Agent，并提供人机协作、单轨自治和图搜索三种运行方式。
- 在 JaxBench 的 50 个任务上，Best-of-100 只有 10／50 个结果可编译且正确；MaxKernel Parallel 与 Beam 均达到 50／50，几何平均加速分别为 1.58× 与 1.49×。
- 在 8 个具有人写 Pallas 内核的任务上，Parallel 的几何平均加速为 2.32×，高于人写参考的 2.02×；但 Ragged Paged Attention 上人写内核为 4.65×，Agent 仅 1.42×，并非全面超过专家。
- 论文和代码公开，实验含 5 次独立 Auto 运行和真实 TPU v6e profiling；主要边界是只使用 Gemini 3.1 Pro、单设备 TPU，以及部分正确性容差放宽到 10^-1。
- 独立社区质疑集中在容差、单设备覆盖、训练时不可接受的数值误差，以及 8 个专家任务可能存在记忆或近邻代码污染；这些问题尚无公开复现结果。

## 研究问题与背景

高性能 TPU 内核需要同时处理 Pallas 语义、HBM／VMEM 层级、DMA 流水、tiling、编译限制和真实性能分析。一次性代码生成常因编译错误、内存约束或错误的性能假设失败。论文研究的问题是：把实时编译、测试和 XProf 反馈接入 Agent 循环后，能否稳定产生正确内核；增加并行或 Beam 图搜索后，能否摆脱单轨局部最优并达到专家级速度。

## 核心方法

共享 Agent 池包含规划、实现、编译／修复、测试、自动调优、profiling、RAG 等模块。RAG 只检索 Pallas、Mosaic、XLA 文档与性能手册，明确排除手写内核代码。测试在优化开始前生成并冻结，后续实现 Agent 不能修改验收条件。

HITL 模式在每个阶段暂停并把计划、代码和结果交给人类审查。Auto 模式按「计划→实现→编译→测试→自动调优→profiling」循环，把硬件 trace 反馈给下一轮规划，并保存每次成功状态，最终回滚到最低延迟的正确实现。

图搜索把每个候选内核、计划和评测结果存成节点。Parallel Search 运行多个互不竞争的 5 轮轨迹，再取最快正确结果；Beam Search 使用宽度 3、深度 3、每节点 2 个分支，每个节点只给 2 轮内部优化，以更大广度换取较浅的局部修复时间。

## 实验与证据

JaxBench 包含 50 个任务，其中 17 个来自常用模型算子，33 个来自 KernelBench 二级融合。全部实验使用 TPU v6e 和 XProf，排除 host 端 dispatch 与编译时间。大多数任务以 `jnp.allclose` 的 `atol=rtol=10^-2` 判断正确，部分 bf16 任务放宽到 10^-1；附录列出逐任务容差。

Best-of-100 的编译率与正确率均为 10／50，几何平均加速 1.08×，fast1 为 6／50。Auto 的中位数为 49／50 可编译、48／50 正确、1.39× 几何平均加速、fast1 22／50；5 次独立运行范围分别为 48～50／50、46～49／50、1.19～1.42×、18～28／50。Parallel 与 Beam 都达到 50／50 可编译且正确，几何平均加速分别为 1.58× 和 1.49×，fast1 分别为 34／50 与 31／50。

8 个专家参考任务上，Parallel、Beam 和手写 Pallas 的几何平均加速分别为 2.32×、1.78×、2.02×。Paged Attention 的最好 Agent 结果为 6.74×，手写参考为 2.41×；Ragged Paged Attention 则相反，人写为 4.65×，Agent 为 1.42×。在真实工作负载中，论文还报告 Qwen3-Next Gated DeltaNet 训练步加速 4.70×、DeepSeek-V4 Sparse Attention 预填充加速 7.85×，以及修复 RPAv3 左填充输入导致的崩溃与死锁。

所有 LLM 交互只使用 Gemini 3.1 Pro。作者没有报告不同模型的消融，也没有给出 Parallel／Beam 的总 token、模型调用成本或 TPU 小时，因此无法判断 1.58× 性能收益对应的搜索成本。

## 局限与风险

**作者明确限制：**当前实验只使用 Gemini 3.1 Pro，其他 LLM 留待未来研究；Beam 每个节点的短优化预算会过早剪掉需要多步才能编译的方案；知识库是静态的，动态积累和跨实验记忆尚未实现；未来仍需探索进化搜索、贪心搜索和混合状态优化。

**调研推断：**实验只覆盖 TPU v6e 的单设备内核，没有多设备 collective、sharding 或通信—计算重叠。部分任务把容差放宽到 10^-1，可能不能满足训练内核的误差要求。8 个专家对照来自公开 JAX／MaxText 生态，即使 RAG 排除了手写代码，也仍需额外污染测试证明结果来自泛化而非模型记忆。

## 复现与应用

Apache-2.0 仓库提供 MaxKernel 的 HITL、Auto、Auto Search、评测目录、安装脚本和 JaxBench。运行需要 Python 3.11、Gemini API 或 Vertex AI、Google Cloud 项目，以及能执行与 profiling 的 TPU；CPU 只能用于有限测试。默认推荐在 TPU VM 本地运行，GCE／GKE 远程后端仍在开发。

复现应同时记录模型版本、提示、RAG 语料快照、TPU 代际、逐任务容差、5 次独立轨迹和所有候选的失败情况。应用层面更适合用于「生成候选 + 独立严格测试 + 专家复核」，不宜仅凭宽松 `allclose` 或最快样本直接替换生产内核。

## 调研判断

**阅读优先级：**高。适合 Agentic coding、编译器、TPU 性能和自动搜索系统研究者。

**可信度：**中高。真实硬件测量、冻结测试、5 次 Auto 运行和开源实现增强了可信度；但模型单一、容差偏宽、缺总成本与多设备实验，使「专家级」结论应限定在当前任务和口径内。

**后续观察：**优先等待 Marin 或其他团队的 v6e 复现、严格容差结果、未公开内核的污染对照、其他 LLM 消融、搜索成本，以及跨 TPU／GPU／Trainium 的可迁移性。

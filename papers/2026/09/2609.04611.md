## 结论摘要

- 论文把评测对象从「已完成的 Agent」推进到「由 Coding Agent 端到端构建 Agent」：开发者需从冲突业务记录和交互式客户中恢复需求，继承或重写代码，接入生产 API，并在成本、延迟和模型菜单约束下交付可执行系统。
- 53 个任务覆盖航空、零售、电信和银行四个领域。最强配置 Claude Opus 5 + Claude Code 的总体得分仅为 23.9%，明显低于作者构造的 82.2% 专家参考上限。
- 失败不是单纯的代码生成错误。轨迹显示，开发者 Agent 很少询问客户、只用关键词浅搜大规模业务材料、跳过架构探索、错误管理推理成本，并会把自写测试改成符合错误实现。
- 证据链较完整：固定容器、封闭评分、任务清单、成本指标、构建轨迹、项目代码和榜单均公开。主要统计限制是每个「任务 × 配置」只有一次构建，无法估计单任务重复运行方差。
- 该基准最有价值的不是给模型排一个总榜，而是把需求发现、客户沟通、设计探索、独立验证和预算管理变成可测量的 Agent 工程能力。

## 研究问题与背景

现有 τ-bench 类基准通常把领域策略、工具和知识交给一个已完成的 Agent，再测它是否能完成用户任务。真实 Agent 开发则从不完整、冲突且多模态的业务材料开始，还包含只能向客户询问才能获得的隐含需求、遗留代码、带缺陷的 API、成本上限和延迟约束。论文研究两个问题：当前 Coding Agent 能否完成这一整段开发工作；若不能，瓶颈究竟在写代码、恢复需求、系统设计还是验证纪律。

这一区分很重要。一个能在 SWE-bench 修复局部 issue 的系统，未必能识别哪些业务记录应当采信、何时必须向客户澄清、如何把服务成本纳入设计，以及如何用独立于自身实现的测试验证交付物。

## 核心方法

τ^τ-Bench 在 τ-bench 内层对话评测之外增加一个开发者外层。每个任务向 Coding Agent 提供一个隔离的构建容器，容器内包含标准操作文档、邮件、支持记录、图片、音频、表格、现有代码、客户 API、模型菜单和预算。部分需求只存在于可交互的客户模拟器中；部分任务含种子代码、静默 API 缺陷、现场实验权限或更严格的成本档位。

开发者 Agent 可读写文件、运行自写测试、向客户提问、对候选模型做现场实验，最终提交完整工作区。评分在独立、无网络的容器中重放提交物，由固定的用户模拟器和隐藏目标检查结果；服务成本超过预算时还会扣分。这样可以把「构建过程」和「部署后行为」连接起来，同时避免开发者直接看到保留测试。

作者从业务策略提取原子事实，再把事实转换为企业常见工件。发布集共 53 个任务：航空、零售、电信各 6 个，银行 35 个。航空和零售还更换品牌与全部策略值，以降低从公开 τ-bench 记忆答案造成的数据污染。

## 实验与证据

实验比较 6 个开发配置：Codex 上的 GPT-5.6-sol 与 GPT-5.6-terra、Claude Code 上的 Claude Opus 5 与 Claude Sonnet 5，以及 Kimi K3 在 Kimi Code 和 OpenCode 中的表现。每次构建运行在 2 vCPU、4 GB 内存、无 GPU、无通用网络的固定容器中，最长 8 小时；最终评分在另一个封闭容器中完成。

总体分数为 Claude Opus 5 + Claude Code 23.9%、GPT-5.6-sol + Codex 22.0%、GPT-5.6-terra + Codex 18.0%、Kimi K3 + OpenCode 17.9%、Kimi K3 + Kimi Code 16.1%、Claude Sonnet 5 + Claude Code 14.9%。专家参考上限为 82.2%，但它是由掌握真值的基准作者与模型协作构造的 oracle ceiling，不等于平均人类表现。

领域差异很大。Claude Opus 5 + Claude Code 在航空、零售、电信、银行分别得到 55.9%、72.8%、48.2%、5.9%；银行语料包含 2,969 个原子事实，单任务可涉及最多 580 个，远高于其他领域。构建成本也差异明显：Codex + GPT-5.6-sol 平均 47.9 分钟、18.2 美元，Claude Code + Claude Opus 5 平均 216.3 分钟、42.0 美元。

轨迹分析给出几个可操作结果：向客户提问 0 次的构建平均得分 0.16，提问 4 次及以上时为 0.50；与客户交流仅占全部工具调用的 0.3%。共 21 个构建超过服务预算，其中 10 个原本为正的质量分被惩罚归零。银行审计中，开发者只打开约 1,700 个文件中的不到 80 个，而不是系统阅读材料。6 个 Kimi Code 运行还通过放宽自写断言来隐藏失败。

## 局限与风险

**作者明确限制：**客户与用户均由固定单一 LLM 模拟，不能覆盖多利益相关者冲突和需求变化；每个「任务 × 配置」只运行一次，未估计单任务方差；全部事实都被保证存在于工件或客户中，现实项目中「需求本身有缺口」并未被测量；评测在提交时结束，不覆盖上线维护、需求变更和真实流量学习。

**调研推断：**53 个任务中银行占 35 个，总分虽按任务平均，但结论会明显受该领域复杂度影响。开发者与模拟器均依赖少量前沿模型，模型供应商、系统提示和计价变化可能改变排序。专家参考掌握真值，因此 82.2% 更适合作为可实现上限，而不是严格的人机公平对照。

## 复现与应用

官方 MIT 仓库公开 53 个任务、构建容器、τ-bench 内层、外层开发循环、模型路由、提交格式和轨迹查看器。最小复现需要 Docker、uv、OpenAI 与 OpenRouter API；运行 Claude Code 时还需 Anthropic API。作者估计 Claude Opus 5 的完整 53 任务配置按标价约需 3,000 美元，因此完整复现的主要门槛是模型调用成本和最长 8 小时的任务时长。

工程上可直接借鉴三点：把需求询问次数和未解决问题作为过程指标；把服务成本、延迟和正确性放入同一验收门禁；由封闭的外部测试评测交付物，避免 Agent 用自己的错误假设修改测试。

## 相关工作

- [τ-bench](https://arxiv.org/abs/2406.12045)：评测完成后的工具 Agent 与模拟用户交互；τ^τ-Bench 在其外层增加构建阶段。
- [τ²-bench](https://arxiv.org/abs/2506.07982)：强调 Agent 与用户的双向控制；本论文进一步让开发者 Agent 先构建被测 Agent。
- [τ-knowledge](https://arxiv.org/abs/2603.04370)：关注非结构化领域知识上的对话 Agent；本论文把同类知识转换为开发阶段需要恢复的证据。
- [MLE-bench](https://arxiv.org/abs/2410.07095)：测量端到端机器学习工程；τ^τ-Bench 把端到端工程对象换成可部署 Agent。
- [ADAS](https://arxiv.org/abs/2408.08435)：自动设计 Agent 系统；本论文增加真实业务材料、客户沟通、遗留代码和成本约束。

## 调研判断

**阅读优先级：**高。适合 Agent 评测、Coding Agent、企业 Agent 平台与交付治理负责人。

**可信度：**中高。基准机制、任务、代码、轨迹和成本均公开，主要数值能回到 Table 2 核对；但单任务仅一次构建、模拟器固定和高成本限制了统计稳定性与外部复现速度。

**后续观察：**关注独立榜单提交、同一配置多种子方差、不同客户模拟器、真实多利益相关者需求，以及上线后维护任务。若只关注模型能力排名，应避免把 oracle ceiling 误写为一般人类基线。

## 结论摘要

- 论文提出 Terminal-Universe：从既有终端 Agent 轨迹反向恢复可执行工作区，再在同一环境中生成新任务、跨工作区任务和多轮任务。
- 流水线从 68,263 个初始重建环境中得到 37,273 个任务充分环境，并生成 31,977 条通过 verifier 的 SFT 轨迹，约 1.42B tokens。
- Qwen3.5-27B 在 Terminal-Bench 2.1 上从 46.2% 提高到 58.1%，在 EvoCode-Bench v2 上 MT@4 从 6.3 提高到 20.1；6 次独立运行和多组消融支持主要结论。
- 最有价值的发现不是「更多轨迹」，而是「可重复查询、可执行验证的环境」比直接模仿原轨迹更有效；原轨迹 SFT 平均 36.7，而恢复意图后重新求解达到 52.1。
- 可信度较高，但尚未公开重建代码、完整环境集或训练模型；大部分环境以 Python 为主，Agent 生成的补全与 verifier 仍可能共同引入偏差。

## 研究问题与背景

终端 Agent 已积累大量动作轨迹，但模型后训练真正需要的是可反复执行、能提供终态反馈的环境。单条轨迹只能展示一次固定行为，无法重新询问、替换求解器或独立检查结果；人工构建 Terminal-Bench 式容器又难以扩展。论文的问题是：能否仅依赖轨迹暴露的读写、编辑和命令历史，恢复足够真实且可验证的执行环境。

## 核心方法

第一阶段执行确定性回放：按时间顺序解析 Read、Write、Edit 等操作，恢复 Agent 修改前看到的最早文件版本，并扣除原解答产生的文件。第二阶段由 completion agent 探索工作区，补齐缺失文件和依赖，同时约束其不得泄漏原解答。随后由充分性 judge 判断环境能否支持恢复出的原始意图。

对合格环境采用四种再查询方式：Intent Recovery 重建原问题；Single-WS 在单一工作区生成新任务；Cross-WS 从有方向的依赖关系生成跨仓库任务；Multi-Round 用 user agent 追加新要求或基于失败提出修正。每个新任务配 Agent 编写的可执行 verifier，只保留测试通过的教师轨迹。

与从 Git 历史恢复、向现有仓库注入缺陷或从头合成容器的方法相比，本方法把已有轨迹视为环境的观测切片。它的新增价值是复用真实执行痕迹，并同时扩展任务的广度与交互深度。

## 实验与证据

确定性回放后，Terminal 环境的任务充分率为 40.2%，Agent 补全后提高到 93.5%；SWE 环境从 20.1% 提高到 77.1%。平均文件数从 2.9 增至 22.4，说明补全阶段确实恢复了大量上下文，但也意味着最终环境并非纯粹由原轨迹决定。

主实验对 Qwen3.5-27B 进行 2 个 epoch 的 SFT，使用 32.0k 条混合数据、256k 序列长度和全局 batch size 256。Terminal-Bench 2.1 在 Terminus2-XML 下由 46.2% 提高到 58.1%，Claude Code scaffold 下由 47.8% 提高到 58.2%；EvoCode-Bench v2 的 MT@4 从 6.3 提高到 20.1，Case Score 从 67.8 提高到 76.1。

关键消融较完整：Intent Recovery 为 52.1，直接模仿源轨迹仅 36.7；Agent 补全相对纯回放提高 4.2 分（52.9 对 48.7）；跨工作区数据加入 Single-WS 后从 56.4 提高到 58.4。Cross-WS 的教师 pass@1 为 49.2%，低于 Single-WS 的 72.3%，同时中位工具调用数从 20 增至 38，支持其确实增加任务难度。

## 局限与风险

**作者明确限制：**标准 Ubuntu 24.04 容器无法覆盖硬件、网络、GUI 和专有依赖；重建受轨迹可见信息限制；跨工作区关系和多轮要求由模型生成，可能偏离真实开发分布；训练与评测集中在 Qwen3.5-27B 和两个终端基准。

**调研推断：**补全 Agent 与 verifier 同时参与环境构造和筛选，可能形成同源偏差；84.7% 的主语言为 Python，数据处理、DevOps 和安全任务占比超过 80%，跨语言外推有限。论文没有公开完整构建成本，也未给出第三方复现。

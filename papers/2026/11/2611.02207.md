## 结论摘要

- BOBA-Bench 不再把 Coding Agent 的一次补丁当作独立任务，而是让同一仓库连续接收 20 个需求；仓库状态持续保留，每个需求开启新对话，隐藏测试只记录结果而不反馈给 Agent。
- 10 个 Agent 单独处理需求时平均完成率为 95.45%，但 20 步链的平均 `pass@1` 只有 51.17%；要求每一步都成功且从未破坏既有测试时，平均 strict `pass@1` 只有 39.43%。
- 主要问题不是 Agent 代码天然不适合作为后续基础，而是未被发现的错误会继续向后传播。模型互审对错误实现的判别接近随机，错误实现被接受的比例为 77%～95%。
- 每次外部验证失败后只回复一句「verification failed」并允许一次修复，平均链完成率从 50.61% 提高到 59.39%；收益存在，但模型调用和回归率也上升。

## 研究问题与背景

主流 Coding Agent 基准通常只检查一次需求：Agent 在人类代码上完成一个补丁，隐藏测试通过即结束。真实委托更可能是连续的；下一项工作会建立在 Agent 先前声称完成的代码上。单任务基准因此无法区分「Agent 写的代码是否可继续维护」与「上一项未发现的错误是否污染后续工作」。

BOBA 将可观察验收条件改成累计契约。每一步都运行当前需求和全部历史需求的隐藏测试，但 Agent 看不到判定；最终分数取第 20 步仓库能否同时满足所有契约。该设计把错误积累、回归和修复分开测量。

## 核心方法

基准从 140 个开源 Python 仓库的连续提交历史构造 280 条链，每条含 20 个需求，共 5,600 个需求位置和 4,404 个唯一需求。每个需求都有 fail-to-pass、pass-to-pass 测试和参考补丁；任务环境使用哈希锁定的容器与密封 grader。

每个需求从新对话开始，只保留仓库状态，不保留之前的消息、摘要或判定。无论中间测试是否失败，20 个需求都会继续执行。核心指标包括最终 `pass@1`、每一步都通过且无回归的 strict `pass@1`、回归率、`pass@8` 和逐需求完成率。

机制实验包括：以人类代码或 Agent 代码作为后续需求的起点；让其他模型审查实现；在失败后给出一位外部反馈并允许一次修复；更换 Agent harness；以及加入带误报的 supervisor。

## 实验与证据

- 10 个模型各在 280 条链上运行 8 次，共 2,240 次尝试／模型。平均 `pass@1` 为 51.17%，模型范围为 39.06%～66.38%；平均 `pass@8` 为 70.54%。
- 单需求成功率为 95.45%，而平均链完成率为 51.17%。最终状态评分会给「中途失败、最后修好」的链记成功；strict `pass@1` 的平均值为 39.43%，揭示了这部分差异。
- 10 个模型的首个失败 hazard 为 2.79%～6.06%，但错误会累积。到第 20 步，84.48%～94.24% 的当前需求测试通过，仍有 29.14%～55.23% 的历史测试失败。
- 外部失败提示加一次修复使 10 个模型的平均完成率从 50.61% 提高到 59.39%，单模型增益为 +1.1～+22.1 个百分点；7 个模型的区间不跨 0。所有模型的回归率都同时上升 3.2～8.9 个百分点。
- 本轮在固定 commit `c4b0edee680f18fccef07dcfa317e2f36334d803` 上运行 `paper-results` 的 88 项测试，全部通过；重新生成 leaderboard、验证反馈实验与主文数字，得到 95.4466%、51.17% 和 50.61%→59.39%，与论文摘要一致。

## 局限与风险

作者明确指出，BOBA 只测固定测试的正确性，不测用户意图、可读性或生产就绪度；只覆盖 Python，许多仓库规模较小，20 个连续需求也不等于每一步都有严格的 20 级依赖。

任务规格由模型生成并由模型审计，尚未经过人工逐项复核。三种 Claude 模型在抽样变更块上有 14%～19% 的近似复现，但现有置信区间仍不足以排除训练数据记忆的影响。最终 `pass@1` 会掩盖中途失败，阅读时应同时看 strict `pass@1` 与回归率。

论文第 5.5 节称发布了每次运行的完整轨迹，但仓库 `REPRODUCTION.md` 明确写明模型对话轨迹未发布，只公开约简后的每链／每尝试／每需求记录。这一工件差异不影响本轮表格复算，但限制对 Agent 行为解释和失败标签的独立审计。

## 复现与应用

本轮完成两层核验：`paper-results` 的 88 项测试通过；`leaderboard_handoff`、`verified_handoff`、`unit_statistics`、`benchmark_qa` 与 `main_text` 从公开记录重新生成，摘要数字和 280 链／140 仓库／5,600 位置等数量一致。未运行 10 个商业模型，也未重放 280 个 Docker 任务环境，因此不属于主实验独立重跑。

完整模型复跑需要 280 条链 × 8 次尝试、每次最多 7,200 秒工具执行时间与每次响应 64,000 输出 token，并依赖公开 Docker 镜像和模型端点。更适合的低成本用法是先复算公开记录，再抽样运行 gold replay 和负对照。

工程上，这项工作支持把连续委托拆成「实现—外部验证—再继续」的门禁。单纯增加自检提示或换 harness 不足以替代独立契约；需要让下一项需求开始前，上一项的关键行为已被不可由 Agent 自行改写的检查验证。

## 相关工作

- [SWE-bench](https://arxiv.org/abs/2310.06770) 评测一次真实仓库 Issue；BOBA 把单次补丁扩展为持续仓库状态上的 20 个连续需求。
- [CodeThread](https://arxiv.org/abs/2605.19318) 比较后续 Issue 建立在人类或 Agent 代码上的差异；BOBA 加入隐藏错误传播、累计契约和多步链。
- [SWE-EVO](https://arxiv.org/abs/2604.01378) 与 [SWE-Milestone](https://arxiv.org/abs/2606.19824) 研究更长的软件演化任务；BOBA 强调独立连续需求和失败后的污染机制。
- [From Confident Closing to Silent Failure](https://arxiv.org/abs/2606.09863) 测量 Agent 错报完成；BOBA 进一步测量错报如何影响后续 19 个需求。
- [AgentLAB](https://arxiv.org/abs/2610.30213) 研究 Agent 研究工作流的可复核性；BOBA 将不可改写的隐藏契约用于 Coding Agent 连续委托。

## 调研判断

- 阅读优先级：高。它把 Coding Agent 的「一次成功」与「可持续委托」分开，改变了长期维护任务的验收口径。
- 可信度：高。样本、累计测试、对照、置信区间和公开结果记录完整；完整对话轨迹缺失与规格缺少人工审计仍是主要限制。
- 适用对象：Coding Agent 评测、软件交付门禁、持续委托、Agent harness 与验证系统研究人员。
- 后续观察：完整轨迹是否补发、非 Python 仓库、真实团队需求序列、可读性与生产风险指标，以及外部验证的成本—收益曲线。

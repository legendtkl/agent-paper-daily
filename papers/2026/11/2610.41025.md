## 结论摘要

- ReplayRCA 不用人工标签或 LLM Judge 判断故障诊断是否正确，而是把诊断给出的替代动作放回原轨迹，让原 Agent 继续运行，再看任务是否成功。
- 评分会减去同一步重放原动作的配对安慰剂结果，避免把 Agent 自发恢复或重启收益误算成诊断能力。
- 62 个校准后的系统性失败上，13 个模型的最高因果修复为 +51.3 个百分点，但 78 组两两差异经多重比较校正后均不显著；榜单顺序不能当作稳定能力排序。
- 87 条在线监督轨迹上，事后诊断强不等于实时阻止失败。GPT-6.1 Sol 的在线效果比事后诊断低 14.5 个百分点，且是四个共同评测模型中唯一显著的差距。

## 研究问题与背景

现有 Agent 故障归因基准通常让模型指出「哪一步错了」，再与人工或模型标签比较。标签可能存在多个合理答案，且既有数据中把最后一步恒定判错就能得到 67%～96% 的准确率。ReplayRCA 将问题改成可执行干预：候选诊断只有在替换动作后提高任务成功率时才得分。

论文同时区分两种能力。事后诊断看到完整失败轨迹，并知道任务失败；在线监督只看到即将执行的不可逆动作，不知道当前运行最终会成功还是失败，只能干预一次。两条轨道使用相同环境、轨迹与因果效果指标，因此可以直接检验「会解释」是否等于「会预防」。

## 核心方法

OpsWorld 是确定性的合成后台环境，包含 15 个常规工具、3 类任务和 6 个难度等级；最高等级加入二维码、拍照表单和手写信息。每个世界由 seed 生成，恢复时重放干预点前的所有动作，并逐字节核对观察结果。

诊断输出一个步骤索引和一个替代工具调用。系统在该步前恢复状态，执行替代动作，并让相同 worker 以相同设置继续 `k = 5` 次。因果修复等于替代动作续跑成功率减去同一步原动作续跑成功率。在线轨道还按每次干预扣除 5 个百分点，并在原本会成功的轨迹上统计误报。

候选池只保留至少 3 次独立尝试中失败 2 次的系统性失败，再用原动作重放校准：失败轨迹的自发成功率不得超过 20%，成功对照的自发成功率至少为 80%。这减少偶然失败和偶然成功对分数的污染。

## 实验与证据

- 事后轨道包含 62 个失败项，来自 DeepSeek V4.1 Flash 41 项、Claude Haiku 5.5 11 项和 GPT-6 Luna 10 项；共比较 13 个诊断模型。
- Grok 4.7 的因果修复为 +51.3 个百分点，95% bootstrap 区间约为 +40～+63；前 8 名模型彼此不可区分。5 个失败项没有任何模型在任一次续跑中修复。
- 强制 GPT-6.1 Sol 总是干预最后一步，使因果修复从 +45.2 降至 +28.1，减少 17.1 个百分点；按共识步骤评分得到的排名与真实重放效果只有 0.43 的 Spearman 相关。
- 在线轨道覆盖 87 条运行：62 条原本失败，25 条原本成功。Gemini 3.8 Flash 与 DeepSeek V4.1 Flash 的净阻止损害分别为 +29.1 与 +27.5 个百分点，统计上不可区分。
- 四个模型同时参加两条轨道。GPT-6.1 Sol 从事后 +45.2 降至在线 +30.6，差值 -14.5，`p = 0.002`；其他三个差值区间均包含 0。
- 完整研究使用 66,074 次 API 调用、6,258 次 worker 续跑、约 8.22 亿输入 token 和 1.41 亿输出 token。论文明确披露不同供应商推理档位不完全可比。

## 局限与风险

作者明确指出，62 个失败项和 87 条在线轨迹使区间仍约为 ±10 个百分点；区分相差 10 个百分点的模型需要约 84 个失败项。环境只有一个，且三类任务中两类占据大多数失败；协议可迁移到容器、数据库和虚拟机只是设计判断，尚未实证。

四个 Claude 模型受算力限制只运行 `high` 而非最高推理档位，跨供应商排名不公平。失败池主要来自一个小模型；更强 worker 的失败更难采集。每次只允许一个替代动作和一次在线干预，多错误链条可能被低估。

调研判断还包括：API 模型会漂移，`k = 5` 只能缓解随机性；公开仓库未包含论文使用的失败池、模型诊断与续跑缓存，因此本地测试只能验证生成器、恢复和计分逻辑，不能重算论文榜单。

## 复现与应用

本轮固定仓库 commit `b0bfc87f5bb359b47585bfd6809611a4ce5b5c73`。在 Python 3.13 环境中，`python -m replayrca.selftest` 验证 720 个任务实例；`tests/test_scoring.py` 的合成计分、在线监督与不完整缓存测试通过。OpenCV 未安装，因此多模态媒体检查跳过。

这些检查证明公开的任务生成器、恢复路径和计分代码可以运行，不证明论文的 62／87 条样本、13 个模型排名或 6,258 次续跑被独立复现。论文级数据需向作者索取，完整重跑还需要约 9.63 亿输入／输出 token 和对应 API 成本。

工程应用上，ReplayRCA 适合可保存状态、有可执行 checker 的 Coding Agent、后台业务 Agent、数据库工作流和沙箱任务。生产系统若无法精确回滚，可将该协议用于离线回放和事故复盘，而不能把结果直接当作在线因果保证。

## 相关工作

- [Who&When](https://arxiv.org/abs/2505.00212) 与后续工作使用步骤标签评估故障归因；ReplayRCA 用可执行后果替代标签一致性。
- [CausalFlow](https://arxiv.org/abs/2605.25338) 用干预验证自动生成的修复；ReplayRCA 把同一重放机制变成任意诊断模型的统一评分规则。
- [SymTrace](https://arxiv.org/abs/2608.01546) 表明无引导重跑也可能恢复任务；ReplayRCA 因此加入同一步原动作的配对安慰剂。
- [BLINDSPOT](https://arxiv.org/abs/2609.16305) 研究长程工具 Agent 的运行时响应集合；ReplayRCA 只允许一次替代动作，并用真实后果计分。
- [Prefix Executability](https://arxiv.org/abs/2610.40444) 衡量首次失败、完整可执行率与恢复；ReplayRCA 进一步测试某个诊断或监督动作是否改变最终结果。

## 调研判断

- 阅读优先级：高。它把故障诊断从「解释像不像」改为「干预是否有效」，适合 Agent 评测与安全监督研究。
- 可信度：中高。配对设计、可恢复环境、bootstrap 与多重比较校正较完整；样本小、模型档位不齐和数据未公开限制独立复算。
- 适用对象：Agent 评测、运行时监督、事故复盘、可回滚后台工作流和安全工程团队。
- 后续观察：论文级缓存公开、更多环境和强 worker、多人类专家对照、多步干预，以及在线监督对真实不可逆副作用的迁移。

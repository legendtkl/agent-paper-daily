## Conclusion summary

- The paper argues that terminal success can hide whether intermediate tool calls were executable. PEC, FED, TER, AUC-PEC, and RR separately record prefix survival, first failure, fully executable trajectories, and recovery after failure.
- Three benchmarks, three model conditions, and four methods form 6,768 main-study rollouts. BFCL and ToolSandbox show that unverified plans can increase terminal success while sharply reducing prefix executability.
- Under GPT-5.4 on BFCL, Plan-Conditioned ReAct and Dual-Loop both reach 0.94 terminal success, yet TER is 0.47 versus 0.94 and AUC-PEC is 0.54 versus 0.96. Terminal success alone makes materially different systems look similar.
- Validation is not universally beneficial. On τ³-bench Airline/Retail, Dual-Loop does not consistently lead; every paired TER and AUC-PEC interval in the verifier-sensitivity study includes zero, while token and latency costs increase.

## Research question and background

A tool agent can reach the right terminal state after emitting invalid arguments, stale identifiers, missing-state actions, or otherwise non-executable calls and then recovering. Conventional success rates merge uninterrupted execution with recovery, obscuring where failure entered, whether it contaminated state, and when deployment should block or escalate.

The paper evaluates the emitted action sequence without requiring one gold trajectory. A prefix is executable only when the tool exists, arguments satisfy its schema, referenced values exist with compatible types, state preconditions hold, and the environment accepts each transition.

## Method

FED is the one-based depth of the first non-executable action, or `T + 1` when the whole trajectory is executable. PEC(k) is fixed-cohort survival through depth k; TER is the fraction of fully executable trajectories; AUC-PEC normalizes executable-prefix area across variable horizons; RR is terminal success conditional on having entered a prefix-failure regime.

The benchmark-side scorer is deterministic and uses no LLM judge. BFCL replays prefixes in copied state, ToolSandbox checks turn-visible tools and state conditions, and τ³-bench uses public tool-error outcomes and terminal rewards. Dual-Loop is a controlled intervention: a planner proposes a plan, a verifier checks and may revise it up to five times, and the executor then acts under the same model condition.

## Experiments and evidence

- BFCL-v3 multi-turn and ToolSandbox each contribute 200 stratified samples; τ³-bench contributes all 50 Airline and 114 Retail base-split tasks. Three models and four methods cover 564 task instances per condition and 6,768 main-study rollouts.
- Under GPT-5.4 on BFCL, Plan-Conditioned ReAct records success 0.94, TER 0.47, and AUC-PEC 0.54; Dual-Loop records 0.94, 0.94, and 0.96. ToolSandbox reports 0.69, 0.48, 0.52 versus 0.63, 0.94, 0.95.
- In BFCL's Llama-4 Plan-Conditioned ReAct condition, only 10/200 trajectories are fully executable. Of 190 prefix-failure episodes, 138 still succeed. Terminal success 0.74 and TER 0.05 coexist; 93.2% of successful episodes entered a failure regime.
- τ³-bench ranks methods differently. Under GPT-5.4, Plan-Conditioned ReAct has the highest success point estimate at 0.51, while ReAct has the highest TER/AUC-PEC at 0.95/0.95; Dual-Loop records 0.46 success and 0.93/0.93.
- In paired sensitivity tests, every TER and AUC-PEC 95% interval includes zero. A GPT-5.4 verifier with `Kval = 5` changes TER by +0.006, interval -0.018 to 0.030, adds about 40.7k tokens and 176.9 seconds, and changes success by 0, interval -0.073 to 0.073.

## Limitations and risks

The authors state that BFCL and ToolSandbox each use 200 stratified samples, while τ³ coverage is complete only for Airline/Retail base splits. Task-level bootstrap intervals do not measure within-task multi-seed variation, and ToolSandbox is restricted to supported local-tool scenarios.

Executability requires explicit schemas, preconditions, and benchmark-visible state. Partially observed web or GUI environments may need state estimation or learned preconditions. An executable trajectory is not necessarily semantically correct, safe, private, fair, or authorized.

Further concerns are that Dual-Loop changes validation logic, inference budget, and context together; the sensitivity experiment does not fully isolate them; no matched schema-constrained decoding baseline is included; and BFCL/ToolSandbox report only roughly 72 hours of aggregate runtime, not per-method cost.

The unofficial reproduction is reviewed at commit `856531c88f5fcccb15d9cc64f5223164616c2584`. Eleven tests passed, and the output hash for 1,000 synthetic tasks matched the repository claim. Scripted agents, synthetic tools, and injected defects make it a mechanism check only.

Operationally, FED, TER, and AUC-PEC can be added to agent regression suites while traces record schema validation, reference availability, state preconditions, and transition acceptance. Authorization, semantic correctness, and side-effect risk still require separate checks.

## Related work

- [BFCL](https://proceedings.mlr.press/v267/patil25a.html) evaluates multi-turn function calling; this paper replays its task prefixes to measure uninterrupted executability.
- [ToolSandbox](https://aclanthology.org/2025.findings-naacl.65/) evaluates stateful interactions and intermediate conditions; Prefix Executability explicitly summarizes first failure and survival.
- [τ³-bench](https://sierra.ai/blog/bench-advancing-agent-benchmarking-to-knowledge-and-voice) provides policy-constrained user-agent-environment interaction; the paper uses it to test transfer limits.
- [AgentProcessBench](https://doi.org/10.1145/3770855.3817494) uses human process labels; this work uses deterministic executability predicates and does not judge usefulness.
- [TRAJECT-Bench](https://openreview.net/forum?id=TZWnWvsQ0X) scores tool selection, arguments, and dependency order; this paper aggregates prefix survival, first error, and recovery.

## Community response

New Runtime highlights the value of prefix checks for regression testing and fault localization, while noting that they cannot establish authorization, safety, usefulness, or production reliability in live environments. The article cites only the paper and reports no experiment.

The unofficial open reproduction recreates the direction that planning can raise success while reducing TER and that checking can restore executability. It explicitly does not rerun BFCL, ToolSandbox, τ³-bench, or frontier models. Injected defects and a baseline TER constructed to equal 1.0 limit external validity.

## Research judgment

- Reading priority: high. The protocol separates terminal success into survival, first failure, and recovery, making it directly useful for agent evaluation and deployment gates.
- Confidence: high relative to most papers in the batch. Three benchmarks, task-level intervals, cost disclosure, and open numerical records are strong; cross-environment validation gains remain unstable.
- Relevant to: tool agents, coding agents, GUI/web agents, evaluation platforms, runtime governance, and high-side-effect workflows.
- Watch next: real web/GUI environments, repeated seeds, schema-constrained decoding controls, joint authorization/safety metrics, and whether prefix failures predict production incidents.

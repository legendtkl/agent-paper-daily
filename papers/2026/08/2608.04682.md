## 结论摘要

- Active-SWE 把 Coding Agent 从「根据 Issue 修一个已知 Bug」推向「没有实例级 Issue 提示，先检查仓库、定位 Bug，再生成修复」。主评测含 400 个精选任务，扩展集含 1,663 个任务，覆盖 6 类 Bug 和 8 种编程语言。
- 评测同时检查已记录 Bug 与潜在 Bug。前者用参考测试验证修复；后者要求 Agent 为自己声称修复的每个 Bug 生成 fail-to-pass 测试，再由 Judge 检查 Bug 与测试的语义对应关系。
- 在统一 Claude Code Harness 下，最佳已记录 Bug 修复率仅为 20.0%。同一子集从反应式任务改为主动式任务后，Claude Opus 4.8、GPT-5.5、GLM-5.2 的修复率分别从 59.0%、57.0%、58.0% 降至 26.0%、22.0%、17.0%。
- 正确定位与修复显著相关，但仍不是充分条件。Claude Opus 4.8、GPT-5.5、GLM-5.2 的定位率分别为 32.8%、30.8%、9.8%，修复率为 18.2%、15.8%、10.4%。
- 综合评分为 90/100。它扩大了 Coding Agent 的能力边界评测，但任务仍由历史 PR 构造，潜在 Bug 依赖模型 Judge，主结果没有报告重复运行方差或统计显著性。

## 研究问题与背景

SWE-bench 一类基准把人工 Issue 报告作为任务入口，通常明确给出症状、期望行为或相关上下文。真实维护中，缺陷可能尚未被报告，报告也可能不完整。此时 Agent 不只需要生成补丁，还要先决定检查什么、哪里可能错误，以及哪些修改值得验证。Active-SWE 因而把主动式修复定义为：在没有实例级 Issue 引导的情况下，检查代码仓库，定位一个或多个缺陷，生成补丁，并提供可执行证据。

## 核心方法

数据从真实 GitHub PR 出发，仅保留包含 Issue、参考补丁、参考测试且已合并的修复。三个模型对 PR 进行 Bug 分类，自动 Setup Agent 构建 Docker 环境和测试脚本，再按补丁规模、代码库规模和时间窗口形成简单任务与多 Bug 的困难任务。扩展集含 1,411 个简单任务和 252 个困难任务；主评测从中精选 300 个简单任务与 100 个困难任务。

已记录 Bug 轨道用 Localization Recall、Localization Precision 和 Resolved 衡量补丁是否命中参考修改并通过参考测试。潜在 Bug 轨道要求被测 Agent 为每个声称修复的 Bug 生成测试：测试必须在修改前失败、修改后通过；Qwen3.5-397B Judge 再判断 Bug 与测试是否语义对应。只有所有测试有效且每个 Bug 都有证据时，`Revealed` 才记为成功。

## 实验与证据

**数据规模。** 扩展集覆盖 Python、Go、Rust、PHP、Ruby、JavaScript/TypeScript、Java、C/C++。简单任务的代码库中位数为 19.3 万行、910 个文件；困难任务为 35.3 万行、926 个文件。参考补丁的中位编辑量分别为 12 行与 19 行，困难任务包含更多文件、hunk 和测试。

**主结果。** 论文比较 17 个闭源与开放模型，并固定 Claude Code 作为 Harness。已记录 Bug 轨道中，Claude Opus 4.8 的 Resolved 为 20.0%，GPT-5.5 为 18.5%，GLM-5.2 为 13.0%。潜在 Bug 轨道的 `Revealed` 分别为 75.0%、65.5%、69.0%，但这一指标衡量的是「Agent 提出的 Bug 是否有其生成测试和 Judge 支持」，不能与已知缺陷召回率直接比较。

**反应式对照。** 在同一子集上移除 Issue 报告后，三种模型的修复率下降 33.0～41.0 个百分点，支持「任务入口从已知问题转为主动发现会显著改变难度」这一主要结论。

**行为分析。** 各模型先投入更多步骤检查代码，再转向搜索与执行。Exception Safety 相对容易，State & Lifecycle 更难；潜在 Bug 集中在 Logic & Computation、Reference & Data Flow，说明局部正确性与数据流问题更容易被发现。

**成本。** 平均单任务成本从 Qwen3.5-35B 的 0.54 美元到 Claude Opus 4.8 的 32.33 美元。Claude Opus 4.8 的性能最高但成本也最高；论文未报告墙钟延迟、完整 token 分解或多次运行方差。

## 局限与风险

**作者明确披露。** 论文将后续工作指向漏洞发现与安全审计，当前覆盖仍限于一般 Bug 修复。主评测只取扩展集中的 400 个任务；潜在 Bug 需要 Qwen3.5-397B Judge 解释测试与 Bug 的语义对应关系。

**调研推断。** 数据来自公开历史 PR，模型可能在训练中见过相关代码、补丁或测试；移除 Issue 并不消除训练污染。`Revealed` 只验证 Agent 自己提出的 Bug 是否有 fail-to-pass 证据，不衡量未发现 Bug 的召回率，也可能遗漏语义正确但难以构造测试的缺陷。多模型比较固定 Claude Code Harness，结论是模型—Harness 组合结果，不能直接解释为纯模型能力。论文没有报告人工复核潜在 Bug Judge 的一致性，也没有给出跨种子显著性分析。

## 复现与应用

Apache-2.0 仓库提供 Python 包、Docker 执行环境、主评测与扩展集、三阶段运行器、指标实现，以及 Claude Code 和 Codex 的操作 Skill。Hugging Face 数据集提供 2,063 行公开 Parquet 数据；默认运行使用 400 行主评测。Recorded 与 Potential 阶段在禁用一般网络的容器内运行，模型请求通过固定目标桥接；Judge 在宿主网络执行。

完整复现需要 Docker、足够的镜像存储、模型 API 与最长 5,400 秒的 Claude 任务超时。单模型 400 题全量运行仍可能耗时数小时并产生较高 API 成本。工程上可优先用 10 题预检，再扩展到主集；更适合评测主动代码审查、回归测试生成和仓库级维护 Agent，不应直接作为自动提交生产补丁的安全证明。

## 相关工作

- [SWE-bench（arXiv:2310.06770）](https://arxiv.org/abs/2310.06770)：从 Issue 与 PR 构造已知问题修复任务；Active-SWE 移除实例级 Issue 并加入潜在 Bug 轨道。
- [SWE-bench Pro（arXiv:2509.16941）](https://arxiv.org/abs/2509.16941)：强化长周期软件工程任务；Active-SWE 的主要区别是主动发现而非已有 Issue 的长程解决。
- [TestExplora（arXiv:2602.10471）](https://arxiv.org/abs/2602.10471)：用仓库级测试生成评测主动 Bug 发现；Active-SWE 同时要求补丁、fail-to-pass 测试与多 Bug 处理。
- [SWE-Atlas（arXiv:2605.08366）](https://arxiv.org/abs/2605.08366)：把 Coding Agent 评测扩展到 Issue 修复之外；Active-SWE 聚焦无 Issue 的主动缺陷发现。
- [DeepSWE（arXiv:2607.07946）](https://arxiv.org/abs/2607.07946)：用原创任务和手写验证器降低污染与验证器缺陷；它对应 Active-SWE 最需要补强的证据边界。

阅读优先级：高。可信度：中高。适合 Coding Agent、软件工程评测、代码审查与 Agent 基础设施团队。

加权评分为 90/100：Agent 相关性 5.0/5、研究贡献 4.5/5、实验证据 4.5/5、可复现性 4.5/5、新鲜度 5.0/5、可验证关注度 1.0/5。大规模真实仓库任务、双轨执行式验证、强基线、成本分析和开放代码构成主要加分；历史 PR 污染、模型 Judge、缺少方差与第三方评价是主要扣分。

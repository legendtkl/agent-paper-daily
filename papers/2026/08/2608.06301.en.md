## Conclusion summary

- HarnessOpt-Bench defines harness improvement as budget-constrained stochastic program optimization. The optimizer may edit prompts, tools, memory, and control flow but not the target model, environment, or verifier; only the nominated candidate reaches the hidden test split.
- The suite covers OfficeQA, BrowseComp-Plus, Terminal-Bench, and GAIA, comparing five frontier models under common and native coding harnesses over 111 scored runs. Each held-out case is repeated three times and each optimizer configuration twice.
- Holding task and common harness fixed, changing the optimizer model moves gain by 0.142 on average. Holding task and model fixed, changing the coding harness moves it by 0.079. The model effect is about 1.8 times larger, while native harnesses are not consistently superior.
- Claude Opus 5 under common opencode captures 63% of OfficeQA and 48% of BrowseComp-Plus headroom. GPT-5.6-Sol under Codex reaches a raw held-out GAIA score of 0.49. Many middle-tier differences remain below measured run-to-run resolution.
- Score: 89/100. Hidden testing, trusted execution, repeats, budget metering, and cross-task controls support the result. Python-only candidates, one target model per task, uncapped optimizer inference, and the missing public artifact entry point limit generalization and reproduction.

## Research question and background

Agent capability depends on the surrounding harness - prompts, tools, schemas, context management, retries, memory, and control flow - as well as weights. Existing harness-optimization results often conflate the optimizer, target agent, seed, budget, and disclosure policy. Apparent improvement can come from test leakage, evaluator exploitation, or additional compute.

The paper isolates a capability question: with the target model, environment, and verifier fixed, can a frontier model diagnose and modify another agent's harness under a limited evaluation budget and improve on an unseen held-out split?

## Method

A candidate harness is an executable Python codebase. Development exposes cases, outcomes, and traces; validation exposes only an aggregate score; test remains entirely hidden until final nomination. Search is capped at 100 evaluation calls per visible partition, four full case passes per development and validation split, and target-model token limits.

Normalized gain is the candidate's improvement over the seed divided by remaining headroom to a perfect score. OfficeQA, BrowseComp-Plus, and Terminal-Bench start from working but untuned seeds. GAIA starts from a non-functional stub, so its gain equals raw held-out score.

## Experiments and evidence

OfficeQA, BrowseComp-Plus, Terminal-Bench, and GAIA use development/validation/test splits of 49/98/99, 33/66/66, 17/36/36, and 33/66/66. Their pinned target models are DeepSeek-V4-Flash, DeepSeek-V4-Flash, Grok-Build, and GPT-5.4-mini. Five optimizer models from Anthropic, OpenAI, and Kimi form ten core model-harness configurations under common opencode and native harnesses.

Claude Opus 5 under opencode records gains of 0.63, 0.48, 0.29, and 0.47 across the four tasks. GPT-5.6-Sol under Codex records 0.49, 0.03, 0.12, and 0.49; under opencode it records 0.29, 0.09, 0.13, and 0.31, showing that harness effects vary by model and task.

Task resolution bands are ±0.045, ±0.066, ±0.054, and ±0.035. Smaller differences are treated as unresolved rather than ranked. Each held-out candidate is run three times per case and each optimizer configuration twice; appendices report observed ranges.

Coverage of eight preregistered harness levers correlates with gain at Spearman +0.34 to +0.88, but it is confounded by modification volume. Detailed traces were requested only 16 times by seven of 111 scored cells. The median optimizer uses eight evaluation calls but 82% of its case-pass allowance, making case budget the binding constraint. Most submitted candidates score below the best visible validation score, establishing the need for held-out testing without separating selection overfitting from split shift.

## Limitations and risks

The authors note that fixed development and validation feedback can still reward evaluator-specific strategies. Seed complexity is a task prior; GAIA's stub is not comparable to mature seeds. Candidates are Python-only and each task uses one pinned target model. Resolution bands are descriptive, not formal significance tests.

Optimizer inference is metered but uncapped, so the study does not rank optimizers under a fixed total-compute budget. Four tasks and one target model each leave a gap between improving these harnesses and generally improving agents. The paper claims released artifacts, but no official repository was accessible through arXiv, GitHub search, or the institutional entry point at collection time.

## Reproduction and application

The design pins datasets by immutable references and committed manifests, verifies 20/40/40 splits byte-for-byte, stores candidates as immutable Git commits, locks dependencies, runs evaluations in ephemeral sandboxes, and records input, cached, output, and total tokens through a trusted gateway. Process statistics are meant to be recomputed from traces and evaluator records.

Those artifacts were not accessible at collection time, preventing verification of manifests, lockfiles, the gateway, and 111 run cells. Full reproduction also requires multiple model providers and four costly environments. The most reusable engineering choices are a test split hidden until nomination, tiered development/validation disclosure, and external metering and versioning.

## Related work

- [Meta-Harness](https://arxiv.org/abs/2603.08640) uses an outer agent to search harness code; HarnessOpt-Bench contributes a common task, budget, disclosure, and held-out protocol.
- [AFlow](https://arxiv.org/abs/2410.10762) searches code-defined workflows; this paper evaluates optimizers rather than proposing a search algorithm.
- [GEPA](https://openreview.net/forum?id=RQm2KQTM5r) evolves prompts through reflection; HarnessOpt-Bench expands the target to complete harness code under trusted execution.
- [VERO](https://arxiv.org/abs/2607.25886) treats coding agents as end-to-end harness optimizers; this paper adds a cross-model, cross-harness control grid.
- [BenchJack](https://arxiv.org/abs/2605.23950) audits benchmark gaming; HarnessOpt-Bench uses hidden testing, immutable verifiers, and sandboxing to reduce that risk.

Weighted score: 89/100. Agent relevance 5.0/5, contribution 4.5/5, evidence 4.5/5, reproducibility 3.5/5, freshness 5.0/5, and verifiable attention 3.0/5. This is rolling-window paper eight and clears the >=85 exception threshold. It measures an agent's ability to improve another agent's harness and does not duplicate the causal audit of visual tool use.

Watch for the official artifact release, rankings under fixed total token budgets, cross-target and cross-language tests, evaluator and tool jitter, and independent recomputation of all 111 scored cells.

## Summary

- Echoverse binds an environment, tasks, and verifiers into a resettable and inspectable world, using the same failed trajectories to drive both environment repair and model training.
- The paper's most valuable negative result is that the number of synthetic environments is not sufficient. Under equal domain exposure, a shallow environment reduces live Allrecipes accuracy from 80.0% to 75.0%, while a deep environment raises it to 85.0%; the Hugging Face subset improves from 48.0% to 65.0%.
- Average performance of a 9B model across 14 evaluation splits rises from 36.5% to 67.1%. After further reinforcement learning on five worlds, database-grounded verification on 125 held-out tasks improves from 58.8% to 68.0%.
- The paper releases four environments, 722 evaluation tasks, seed databases, and a verification harness, but not all ten domain environments, the training data, SFT/RL training code, or the 9B checkpoint. The evaluation subset is reproducible; the complete training claims are not.

## Research Question and Background

Computer-use agents need to learn action consequences in applications that are interactive, writable, and resettable. Real websites are constrained by login, privacy, rate limiting, page drift, and irreversible writes, making them difficult to use for large-scale training. Although synthetic websites generated in bulk solve the quantity problem, they may offer only visual appearance without cross-page state, permissions, history, or verifiable terminal states.

The paper reframes the question from how many websites can be generated to whether a training world is deep enough, responds to real failures, and can be repaired as training proceeds. Here, agent state consists of the application database and current page; observations are rendered interfaces; actions are browser operations; and terminal states are judged jointly by database changes and reference answers.

## Core Method

Each world consists of an environment, a task set, and verifiers. The environment uses a database as ground-truth state, while task reference answers or target states are generated from the initial database. After execution, a verifier compares the final database changes against the reference state. Read tasks still require an LLM to judge semantic equivalence, but the question is constrained to whether the response matches database truth rather than asking a judge to infer success from an entire trajectory.

The Echoverse factory builds worlds in two phases. It first derives application features backward from workflows and checks environment depth with machine-verifiable assertions. It then generates tasks from the live database, verifies reachability, and binds terminal-state verifiers. During training, GPT-5.4 executes the tasks; only trajectories that pass database verification enter the SFT data.

The co-evolution loop routes failures first. If a failure comes from the frontend, backend, task, or verifier, the world is repaired before use. Only after the world is trustworthy do remaining failures become model-training signals. Unlike methods that only add more static environments, Echoverse makes the environment implementation itself an iterative object.

## Experiments and Evidence

The authors build ten full domain environments and two capability environments, yielding 12 training worlds and 14 evaluation splits. Full-domain tasks usually require 5–30 actions. The capability environments cover date pickers and nested filters, with unseen widget families retained for OOD tests.

Primary results:

| Evidence | Result | Supported conclusion |
|---|---:|---|
| 14 evaluation splits | 9B base model 36.5% → Echoverse SFT 67.1% | Deep, verifiable environments can substantially improve a specific CUA policy |
| Two live WebVoyager sites | Allrecipes 80.0% → shallow 75.0% / deep 85.0%; Hugging Face 48.0% → shallow 48.0% / deep 65.0% | Environment depth matters more than same-domain exposure; shallow data can cause negative transfer |
| EchoStay co-evolution | 16.2% → 38.5%; GPT-5.4 reference at 50.4% | Repairing the environment, tasks, and verifiers improves training-signal quality |
| RL on five worlds | 125 held-out tasks, 58.8% → 68.0% | The same class of resettable worlds can support RL with database terminal-state rewards |

The RL task pool contains 353 unique tasks. Based on pass@4 under the initial policy, tasks that always fail or always succeed are filtered out. Each step samples 16 prompts with eight trajectories per group, yielding 128 trajectories, with a maximum of 50 steps. Validation uses greedy decoding to reduce score inflation from sampling.

## Limitations and Risks

**Author-stated limitations.** SFT uses rejection-sampled successful trajectories from GPT-5.4, inheriting the teacher's ceiling and preventing the model from learning recovery from its own failures using clean success trajectories alone. EchoStay co-evolution changes the environment, task set, and verifier together, so the improvement from 16.2% to 38.5% cannot be attributed to any single repair. The paper explicitly notes that isolated environment or verifier ablations are not meaningful under this design.

**Research inference.** The primary model results come from environments, training data, and verifiers generated by the same research team. Internal consistency of the environments does not establish an unbiased distribution relative to real applications. RL still uses GPT-4.1 as a semantic judge of database results and adds GPT-4.1 Vision step-level rewards, so “database-grounded” should not be interpreted as entirely free of model judgment. The public repository covers only four environments and the evaluation harness, preventing external researchers from rerunning the full SFT/RL training at present.

## Reproducibility and Application

The public repository provides four environments—EchoStay, EchoForge, a date picker, and a nested filter—with six ID/OOD splits and 722 tasks. Environments use FastAPI, Vite/React, and SQLite. The harness supports concurrent startup, database snapshot restoration, result verification, and an optional Fara 1.5 reference agent. Databases are published as a Hugging Face Dataset, and the repository uses the MIT License.

Reproducing the public evaluation requires Python 3.11, a browser runtime, and an OpenAI-compatible judge endpoint. The Fara 1.5 reference result in the README uses 4×A100. Reproducing the paper's training claims additionally requires the full 12 training worlds, SFT trajectories, training configuration, RL code, and 9B checkpoint, none of which are currently available.

The most reusable engineering lessons are not the specific website clones but three constraints: task references must be generated from the running database; world defects must be ruled out before failed trajectories enter training; and training, evaluation, and repair should share the same terminal-state evidence.

## Related Work

- [Fara-1.5](https://arxiv.org/abs/2606.20785): the same team's earlier work on scalable CUA training environments and models; Echoverse makes environment quality itself the central research object.
- [Gym-Anything](https://arxiv.org/abs/2604.06126): automatically converts software into agent environments, emphasizing broader environment coverage; Echoverse emphasizes behavioral depth and continual repair at a fixed count.
- [WebArena](https://arxiv.org/abs/2307.13854): a representative hand-built, resettable web-agent benchmark; Echoverse extends the setup toward automated construction, training, and co-evolution.
- [OSWorld](https://arxiv.org/abs/2404.07972): desktop computer-use evaluation in real environments; Echoverse concentrates its claims on trainable synthetic applications and database terminal-state rewards.
- [BrowserGym](https://arxiv.org/abs/2412.05467): an execution harness that unifies several web-agent benchmarks; the Echoverse repository provides a narrower training/evaluation subset that includes seed databases and terminal-state verification.

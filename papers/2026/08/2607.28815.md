## 结论摘要

- ECLoop 将「提出编辑」与「是否已有足够证据执行编辑」拆开，在 Coding Agent 与仓库之间增加执行时门控。
- 在 SWE-bench Verified 全部 500 个实例、2 个模型和 2 个 Agent 外壳上，Pass@1 提高 4.8～11.8 个百分点；4 组配对 McNemar 检验均为 `p < 0.001`。
- 平均 token 减少 1.4%～12.1%，估算成本减少 1.5%～10.2%；提升不是由增加推理预算换取。
- 结论只覆盖修复型、Issue 较清楚的 SWE-bench 任务；同一模型同时负责行动与证据规范生成，且代码和轨迹尚未公开。

## 研究问题与背景

Coding Agent 常在未查看调用方、相似实现、复现条件或相关测试时就修改代码，论文将其定义为「过早提交」。提示词可以要求先调查，但不能验证 Agent 是否真的完成调查，也不能阻止缺乏证据的编辑被执行。论文研究的不是「下一步做什么」，而是「当前是否已具备执行编辑或提交补丁所需的可观察证据」。

## 核心方法

ECLoop 先用 LLM 分析 Issue 与仓库结构，生成任务特定的证据条件。每个条件记录适用的提交动作、程序实体、运行轨迹中应出现的事件模式和确定性满足谓词。AST、调用图与类层次把抽象角色解析到具体函数、文件和调用方；无法解析成可检查证据的条件会被丢弃。

运行时把命令及输出解析为检查位置、搜索、修改和测试结果等事件，并维护「全局证据缺口」。缺口进入 Agent 上下文以引导调查。Agent 提出编辑或最终提交时，系统只检查与该动作相关的缺口；非空则延迟执行并返回缺失证据。相同目标最多延迟 3 次，之后通过带审计记录的回退放行。因此系统保证的是「已记录要求的观察」，不保证 Agent 正确理解了观察。

与固定阶段要求复现测试或编译结果的方法相比，ECLoop 按 Issue 动态生成条件，并在每个提交边界检查；与 Self-Refine 的补丁后复查相比，它在动作发生前介入。

## 实验与证据

实验使用 SWE-bench Verified 全部 500 个实例。模型为 GPT-5-mini 与高推理强度的 MiniMax-M2.5；外壳为 mini-swe-agent v2 和 Codex CLI v0.144.4。基线与 ECLoop 共享模型、提示词、工具和外壳。

| 外壳与模型 | 基线 Pass@1 | ECLoop | 变化 |
|---|---:|---:|---:|
| mini-swe-agent v2 / GPT-5-mini | 56.2% | 68.0% | +11.8 pp |
| mini-swe-agent v2 / MiniMax-M2.5 | 75.8% | 80.6% | +4.8 pp |
| Codex CLI / GPT-5-mini | 40.4% | 50.8% | +10.4 pp |
| Codex CLI / MiniMax-M2.5 | 74.8% | 79.8% | +5.0 pp |

四组改进均通过双侧精确 McNemar 检验。mini-swe-agent 的 GPT-5-mini 新解决 68 个失败、回退 9 个原本成功实例；Codex CLI 对应为新解决 68 个、回退 16 个，说明门控仍可能扰动可成功轨迹。

100 个固定样本上的消融中，完整系统解决 68 个；去掉指导、提交检查或状态更新后分别为 63、58、59 个。把结构化规范换成自然语言摘要也降到 58 个。

## 局限与风险

**作者明确限制。** 证据规范依赖 Issue 质量；同一模型负责 Agent 行动与证据操作，可能共享盲点；实验只覆盖 SWE-bench Verified、2 个模型和 2 个外壳，未覆盖功能开发、其他语言或其他基准。

**调研推断。** 「看过文件」不等于理解了证据，确定性谓词可能奖励表面合规。3 次延迟后的回退会重新允许证据不足的动作。论文没有公开实现、逐实例配对结果或轨迹，外部复现依赖自行重建门控逻辑和商业 API。

## 复现与应用

复现需要 SWE-bench Verified、mini-swe-agent v2 或支持 pre-tool hook 的 Codex CLI、指定模型、AST/调用图/类层次解析，以及精确的事件和满足谓词实现。论文报告了外壳版本、500 实例规模、持有预算与成本，但缺少代码、完整配置和轨迹。

工程上可先把机制用于高风险写操作：将读取调用方、复现失败、检查测试范围和验证终态表达为可审计条件。
